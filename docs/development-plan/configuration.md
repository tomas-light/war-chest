# Конфигурация и feature flags

Конфигурация приложений и feature flags решают разные задачи. Конфигурация описывает адреса сервисов, таймауты и параметры авторизации. Feature flags — внешние runtime-переключатели, которыми можно управлять независимо от сборки и деплоя приложения.

Мы не смешиваем эти механизмы: числовой таймаут не становится флагом, а секрет авторизации не попадает в JSON, который можно отдать браузеру.

## Конфигурация приложений

У каждого приложения есть собственные файлы:

```text
apps/server/
  env.yaml
  env.local.yaml

apps/web/
  env.yaml
  env.local.yaml
```

`env.yaml` содержит структуру конфигурации и безопасные значения по умолчанию. Он хранится в Git.

`env.local.yaml` необязателен, переопределяет отдельные значения из основного файла и не попадает в Git. В нём находятся адреса, секреты и настройки конкретного разработчика.

Загрузчик не определяет окружение и не содержит отдельных условий для `localhost`, `dev` или `production`. На стендах `env.local.yaml` просто отсутствует: файл игнорируется Git и не включается в артефакты сборки или Helm chart.

Приоритет:

```text
env.yaml
  < env.local.yaml, если файл существует
  < явно переданные переменные процесса сборки или запуска
```

Явные переменные имеют наивысший приоритет. Для клиента это переменные процесса `build`, для сервера — процесса `start`. Серверные секреты передаются при запуске, а не встраиваются в собранный JavaScript.

Конфигурация плоская. Каждый файл содержит только пары `KEY: value`, где значением может быть строка, число или boolean. Вложенные объекты и массивы не используются.

Ключи записываются в `UPPER_SNAKE_CASE` и напрямую соответствуют одноимённым переменным процесса. Каждый следующий источник просто заменяет значение совпавшего ключа.

Загрузчик должен:

- искать файлы относительно корня конкретного приложения;
- читать `env.local.yaml`, если файл существует;
- корректно работать без него;
- работать только с плоскими ключами;
- переопределять значения простым присваиванием по ключу;
- последними применять явно переданные переменные;
- проверять итоговую конфигурацию по типизированной схеме;
- завершать запуск или сборку при неизвестных ключах и неверных типах;
- отдавать остальному коду только проверенную плоскую конфигурацию.

### Сервер

Пример структуры:

```yaml
APP_HOST: "0.0.0.0"
APP_PORT: 3000
DATABASE_URL: "postgres://war_chest:war_chest@localhost:5432/war_chest"
GOOGLE_CLIENT_ID: ""
TELEGRAM_CLIENT_ID: ""
TELEGRAM_CLIENT_SECRET: ""
DISCONNECTED_PLAYER_TIMEOUT_MINUTES: 15
SNAPSHOT_EVERY_EVENTS: 100
FEATURE_FLAGS_RUNTIME_FILE: "../../runtime/feature-flags/feature-flags.localhost.json"
```

Сервер читает YAML во время запуска. Секреты Google или Telegram нельзя добавлять в основной `env.yaml`.

`DISCONNECTED_PLAYER_TIMEOUT_MINUTES` задаёт, сколько минут незавершённая партия ждёт отключившегося игрока. Таймер начинается, когда у игрока не остаётся ни одного активного соединения. После истечения времени игроку засчитывается поражение.

`SNAPSHOT_EVERY_EVENTS` задаёт интервал сохранения снимков. При значении `100` сервер создаёт snapshot после каждого сотого игрового события. Значение `0` отключает автоматическое создание snapshots.

Snapshot не считается событием и не увеличивает sequence number. Это производный кэш: цепочка событий остаётся единственным источником истины.

### Клиент

Пример структуры:

```yaml
API_BASE_URL: "http://localhost:3000"
SOCKET_URL: "http://localhost:3000"
GOOGLE_CLIENT_ID: ""
DEVELOPER_PANEL_ENABLED: false
```

Клиентский YAML читается во время сборки Vite. Явные переменные команды сборки применяются после YAML и имеют наивысший приоритет. Любое итоговое значение оказывается доступным в браузере, поэтому в `apps/web/env.yaml`, `apps/web/env.local.yaml` и build-переменных клиента не должно быть секретов.

Dev-панель отображается только в development-сборке и при `DEVELOPER_PANEL_ENABLED: true`.

## Runtime feature flags

Feature flags не входят в `env.yaml`, образ контейнера или клиентскую сборку. `env.yaml` содержит только путь к внешнему файлу активного окружения и параметры механизма перезагрузки.

Для каждого окружения существует один самостоятельный файл с полным набором флагов:

```text
feature-flags.production.json
feature-flags.dev.json
feature-flags.localhost.json
```

Пример содержимого:

```json
{
  "gameHistory": true,
  "spectatorMode": true,
  "optimisticMoves": false
}
```

В файле находятся только boolean-значения. Секретов, адресов и числовых параметров в нём нет.

При добавлении новой функции её флаг сначала добавляется со значением `false` во все три файла окружений. После развёртывания кода нужное окружение можно включить простой runtime-заменой его файла, без повторной сборки и деплоя приложения.

### Как обновляется флаг

Новая версия файла подкладывается без пересборки приложения:

1. Система управления конфигурацией записывает полный JSON под временным именем рядом с активным файлом.
2. После полной записи временный файл атомарно переименовывается в имя активного файла окружения.
3. Уже идущие игры продолжают использовать ранее сохранённые значения.
4. При старте следующей игры сервер читает новую версию файла.
5. Новый snapshot записывается в событие `GameStarted`.

Атомарное переименование не даёт серверу прочитать частично записанный JSON.

Сервер не следит за файлом и не обновляет глобальное состояние в фоне. Чтение происходит на границе игровой сессии — при обработке команды старта. Обновление флагов не требует рестарта сервера или нового deployment cycle.

Отдельной проверки схемы, полноты набора или списка известных ключей нет: содержимое JSON считается готовым runtime snapshot.

### Размещение файлов

Для локальной разработки используется:

```text
runtime/feature-flags/feature-flags.localhost.json
```

Локальный runtime-каталог игнорируется Git. В `dev` и `production` рекомендуемый вариант для одного сервера — read-only bind mount соответствующего файла:

```text
dev:
  host:      /opt/war-chest/feature-flags.dev.json
  container: /runtime/feature-flags/feature-flags.dev.json

production:
  host:      /opt/war-chest/feature-flags.production.json
  container: /runtime/feature-flags/feature-flags.production.json
```

В каждом deployment server config указывает через `FEATURE_FLAGS_RUNTIME_FILE` только на файл своего окружения. Образ приложения не содержит актуальных значений флагов. Их жизненный цикл принадлежит runtime-инфраструктуре.

Если позже появится несколько экземпляров сервера одного окружения, все они должны получать один и тот же файл из общего источника. Файлы разных окружений никогда не объединяются и не переопределяют друг друга.

## Helm и Kubernetes

Helm хорошо соответствует нашей модели конфигурации, но использовать его имеет смысл только вместе с Kubernetes. Он не является самостоятельной заменой Docker Compose или обычному запуску на виртуальной машине.

Если проект перейдёт на Kubernetes, структура может выглядеть так:

```text
deploy/helm/war-chest/
  Chart.yaml
  values.yaml
  values-dev.yaml
  values-production.yaml
  templates/
    server-configmap.yaml
    web-configmap.yaml
    feature-flags-configmap.yaml
    deployment.yaml
    service.yaml
```

Приоритет Helm values совпадает с требуемой моделью:

```text
values.yaml
  < values-<environment>.yaml, переданный через -f
  < параметры командной строки --set / --set-string / --set-file
```

`values-dev.yaml` и `values-production.yaml` содержат различия окружений. Разовые явные значения передаются через командную строку и имеют наивысший приоритет.

Feature-flags JSON можно передать в chart через `--set-file` и сформировать из него Kubernetes ConfigMap. ConfigMap монтируется в Pod как каталог:

```text
/runtime/feature-flags/feature-flags.<environment>.json
```

Нельзя монтировать файл через `subPath`: такой mount не получает обновления ConfigMap. При обычном ConfigMap volume Kubernetes обновляет файл после синхронизации kubelet. Сервер прочитает новую версию при старте следующей игры, а уже идущие партии продолжат использовать флаги из `GameStarted`.

Обновление ConfigMap не требует новой сборки образа. Если шаблон Deployment не меняется и в Pod template нет checksum-аннотации для этого ConfigMap, отдельный rollout приложения тоже не нужен.

Для текущего MVP Kubernetes и Helm откладываем. Их стоит добавлять вместе, когда появится реальная потребность в Kubernetes: несколько экземпляров сервера, автоматическое восстановление Pod, единое управление окружениями или уже существующий кластер.

## Загрузка при инициализации приложения

Сервер предоставляет:

```text
GET /config/feature-flags.json
```

Endpoint при запросе читает runtime-файл активного окружения и возвращает его содержимое без дополнительной проверки схемы.

Клиент вызывает endpoint один раз во время инициализации приложения. Полученный snapshot используется для:

- общего layout и навигации;
- разделов вне активной игры;
- UI-возможностей, не влияющих на игровую механику.

Фонового обновления и Socket.IO-уведомления нет. Если runtime-файл изменился после инициализации, общий UI получит новые значения после следующей загрузки приложения.

## Фиксация флагов в истории игры

При выполнении команды старта сервер:

1. Читает JSON активного окружения.
2. Формирует событие `GameStarted`.
3. Записывает полный snapshot флагов в payload события.
4. Сохраняет событие в `game_events`.
5. Передаёт те же значения клиентам вместе с игровым событием.

Пример:

```json
{
  "type": "GameStarted",
  "payload": {
    "featureFlags": {
      "gameHistory": true,
      "spectatorMode": true,
      "optimisticMoves": false
    }
  }
}
```

После сохранения `GameStarted` runtime-файл больше не используется этой игрой:

- сервер проверяет поведение по `game.featureFlags`;
- клиент получает флаги из игрового snapshot;
- reconnect возвращает тот же набор;
- replay восстанавливает значения из события;
- замена файла окружения не меняет уже начатую партию.

Значения, загруженные при инициализации приложения, не используются как источник игровых правил. В момент старта сервер независимо перечитывает файл, поэтому новая партия получает актуальный snapshot даже в давно открытой вкладке.

## Dev-переопределения на клиенте

В development-сборке клиент показывает drawer с feature flags. Для состояния используем отдельный Zustand store с `persist`:

```ts
interface FeatureFlagsDevState {
  gameId: string;
  gameFlags: FeatureFlags;
  overrides: Partial<FeatureFlags>;
  setOverride(name: FeatureFlagName, value: boolean | undefined): void;
  resetOverrides(): void;
}
```

Эффективное значение:

```text
локальное переопределение ?? значение текущей игры
```

Drawer показывает:

- имя флага;
- значение, зафиксированное для текущей игры;
- локальное переопределение;
- итоговое значение;
- сброс одного флага;
- сброс всех переопределений.

Переопределения принадлежат конкретной игре. Они сохраняются в `localStorage` под ключом, включающим `gameId`, поэтому переживают reload и reconnect этой же партии.

При открытии другой игры клиент создаёт отдельное пустое состояние overrides и не переносит значения из предыдущей партии. При явном выходе из игры или после её завершения соответствующий ключ удаляется из `localStorage`.

## Критерии готовности

- каждое приложение читает собственный `env.yaml`;
- конфигурация содержит только плоские строки, числа и boolean-значения;
- вложенные объекты, массивы и deep merge отсутствуют;
- необязательный локальный YAML переопределяет основной и игнорируется Git;
- явно переданные build/start-переменные имеют наивысший приоритет;
- неверная конфигурация останавливает запуск или сборку;
- клиентские конфиги не содержат секретов;
- runtime-файлы не входят в сборку и deployment-артефакт;
- у `production`, `dev` и `localhost` есть по одному файлу с полным набором boolean-флагов;
- сервер читает файл активного окружения только при старте игры;
- новый файл применяется к следующей запускаемой игре без перезапуска;
- сервер не валидирует схему и состав feature-flags JSON;
- клиент загружает runtime-флаги при инициализации приложения;
- старт игры независимо перечитывает актуальный runtime-файл;
- `GameStarted` содержит полный snapshot feature flags;
- начатая игра не меняет флаги после замены runtime-файла;
- общий UI использует initialization snapshot;
- игровая механика использует флаги из события или игрового snapshot;
- dev drawer сохраняет переопределения с привязкой к `gameId`;
- переопределения переживают reload одной игры;
- переопределения не переносятся между играми;
- после выхода или завершения игры локальные переопределения удаляются.
