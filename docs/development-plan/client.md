# React-клиент

Клиент отвечает за интерфейс и удобство игрока, но не принимает окончательных решений о допустимости хода. Он показывает состояние, отправляет команды и применяет подтверждённые сервером события.

HTTP и Socket.IO решают разные задачи: первый работает с аккаунтом и списками игр, второй поддерживает активную партию.

Техническая основа клиента:

- React, Vite и React Router в Declarative Mode; `nice-web-routes` формирует
  типизированные URL;
- TanStack Query хранит request/response server state, а Zustand — долгоживущее
  клиентское состояние и модель активной игры;
- `socket.io-client` доставляет подтверждённые игровые события;
- SCSS и SCSS Modules лежат рядом с компонентами;
- Vitest проверяет unit-контракты, а стабильный `@playwright/test` — компоненты
  через component gallery и целостные E2E-сценарии.

Unit- и компонентные тесты лежат рядом с проверяемыми файлами. Используем
суффиксы `*.test.ts(x)` и `*.ctest.ts(x)` соответственно. E2E-сценарии лежат в
`tests/e2e` и называются `*.spec.ts`. Все браузерные тесты запускаются в
закреплённом Docker-образе Playwright, чтобы браузер, шрифты и скриншоты не
зависели от локальной операционной системы.

## Архитектура

Клиент строим по Feature-Sliced Design (FSD). Такая структура разделяет
приложение по ответственности и не даёт страницам, игровой логике и общим
компонентам постепенно смешаться в одном модуле.

Используем следующие слои:

- `app` — запуск приложения, провайдеры, роутер и глобальная конфигурация;
- `pages` — композиция экранов, соответствующих маршрутам;
- `widgets` — крупные самостоятельные части страницы, например игровое поле
  или панель участников;
- `features` — пользовательские действия: вход, создание игры, присоединение,
  отправка команды и принудительная синхронизация;
- `entities` — бизнес-сущности и их состояние: пользователь, игра, участник;
- `shared` — переиспользуемые UI-компоненты, API-клиенты, конфигурация и
  технические утилиты без игровой бизнес-логики.

Модули импортируют код только из нижележащих слоёв. Слайсы одного слоя не
зависят друг от друга напрямую, а внешний код обращается к слайсу через его
публичный API в `index.ts`.

Предлагаемая структура:

```text
apps/web/src/
  app/
    providers/
    router/
    styles/
    index.tsx
  pages/
    login/
    lobby/
    game/
    user-profile/
    game-history/
  widgets/
    game-board/
    game-participants/
    game-move-history/
    user-profile-header/
    game-history-list/
  features/
    auth/
    developer-tools/
    create-game/
    join-game/
    send-game-command/
    sync-game/
    review-game-segment/
  entities/
    user/
    game/
    game-event/
    game-participant/
  shared/
    api/
    config/
    lib/
    ui/
  main.tsx
```

Внутри слайсов используем сегменты по необходимости: `ui`, `model`, `api`,
`lib` и `config`. Не создаём пустые сегменты заранее.

Все HTTP-вызовы и игровые соединения проходят через контракты и backend gateway
в `shared/api`. Страницы и features не знают, работает клиент с real или fake
backend. Самостоятельный запуск клиента описан в разделе
[«Разработка клиента без сервера»](./client-development/README.md).

Браузер использует один origin. HTTP-запросы начинаются с `/api/`, а Socket.IO
подключается по `/api/socket.io`. В development Vite проксирует эти пути на
Fastify; в production Fastify раздаёт собранный SPA и обрабатывает API сам.

## Основные экраны

```text
/login
/lobby
/games/new
/games/:gameId
/games/play/:gameId
/profile
/users/:userId
/history/:gameId
```

В real-режиме на `/login` доступны официальный Google button, вход через
Telegram OIDC и Yandex ID. Telegram и Yandex запускаются переходом на серверные
`/auth/*/start`. После входа клиент работает только с собственной сессией War
Chest и не хранит токены провайдеров.

В fake-режиме на том же экране остаются кнопки Google, Telegram и Yandex, но
каждая вызывает fake-авторизацию и входит в отдельный seeded fake-аккаунт
соответствующего провайдера. Внешние SDK, popup и redirect при этом не
используются. Страница вызывает общий контракт входа и не знает, какой backend
создаёт сессию.

Профиль содержит `avatarVersion`, а изображение загружается только с нашего API:

```text
GET /api/users/:userId/avatar?v=<avatarVersion>
```

Клиент никогда не вставляет внешний URL Telegram, Google или Yandex в `img`.
Если у пользователя нет сохранённого изображения, показывается локальная
заглушка с инициалами.

### Профиль игрока

У любого игрока есть профиль по маршруту `/users/:userId`. На нём показываем:

- аватар и отображаемое имя;
- список завершённых игр, в которых пользователь участвовал как игрок;
- дату завершения, участников и результат пользователя в каждой игре;
- переход к просмотру выбранной игры через `/history/:gameId`;
- состояние пустого списка и подгрузку следующей страницы истории.

Игры, за которыми пользователь только наблюдал, в его игровую историю не
входят. Список отсортирован от недавно завершённых партий к более старым.

Маршрут `/profile` открывает профиль текущего пользователя. Идентификатор
берётся из сессии War Chest, после чего клиент использует ту же страницу,
виджеты и запросы, что и для `/users/:userId`. Отдельную реализацию личного
профиля и отдельный экран списка `/history` не создаём.

В профиль другого игрока можно перейти из списка участников активной игры и из
истории завершённой партии.

На странице игры должны быть видны:

- текущее публичное состояние;
- участники и их статус подключения;
- чей сейчас ход;
- история ходов игроков;
- доступные текущему игроку действия;
- состояние отправленной команды;
- понятное сообщение о reconnect или рассинхронизации.

Зритель получает обновления без искусственной задержки, но видит только общедоступную часть поля.

## История ходов активной игры

История ходов помогает игроку разобраться в изменениях поля, если он пропустил
действие или не понял, как игра пришла к текущему состоянию. Это локальный режим
просмотра: он не откатывает серверную игру, не останавливает других участников и
не рассылается через Socket.IO.

Одна команда игрока может создать несколько событий, поэтому в интерфейсе
история сгруппирована по принятым командам. Для каждой записи показываем игрока,
понятное описание действия и его место в последовательности ходов. Системные
события, влияющие на состояние, например поражение по таймауту, также входят в
ленту отдельными записями. Номера версий и sequence number игроку не показываем:
они нужны только для внутренней синхронизации клиента с сервером.

Игрок может:

- выбрать начальную и конечную команды и проиграть изменения между ними;
- в качестве конца диапазона выбрать актуальное состояние игры;
- запускать и приостанавливать воспроизведение;
- переходить на одну команду назад или вперёд;
- сразу возвращаться к актуальному состоянию.

При воспроизведении клиент восстанавливает состояние на начало выбранного
отрезка, а затем последовательно применяет безопасные события команд до его
конца. Анимация показывает переходы между этими событиями; отдельные серверные
снимки для неё не создаются.

Границы диапазона включены: воспроизведение начинается с состояния
непосредственно перед выбранной начальной командой, показывает её изменения и
заканчивается после применения конечной команды.

### Последовательность состояний и анимаций

Воспроизведение не сводится к вычислению конечного состояния после нескольких
команд. Клиент проходит команды и их события последовательно, чтобы UI мог
показать переход между состояниями.

Для каждого безопасного события клиент:

1. Сохраняет состояние до события как `beforeState`.
2. Синхронно вычисляет `afterState` через `applyViewEvent`.
3. Передаёт событие, `beforeState` и `afterState` в UI-адаптер анимаций.
4. Если адаптер вернул анимацию, запускает её и ждёт завершения.
5. Фиксирует `afterState` как новое `viewedState`.
6. Переходит к следующему событию, а после всех событий — к следующей команде.

Например, безопасное событие доставки жетона из мешка создаёт анимацию движения
жетона от мешка к месту назначения. Следующая команда не начинает
воспроизводиться, пока эта анимация не завершилась.

Анимация необязательна. Если для события нет UI-анимации, `afterState`
применяется сразу. Если ни одно событие команды не создаёт анимацию, вся команда
воспроизводится без ожидания.

Очередь анимаций относится только к отображению и никогда не задерживает
обновление `liveState`. При остановке воспроизведения, ручном переходе по
истории или возврате в live текущая очередь отменяется, а целевое
`viewedState` заново детерминированно вычисляется из событий. Ошибка или отмена
анимации также не должна блокировать переход к корректному состоянию.

Сопоставление `GameViewEventData` с анимацией находится на клиенте, рядом с
представлением игрового поля. `game-engine`, сервер и сохранённые события не
содержат React-компоненты, длительность анимации или другие детали UI.

### Актуальное и просматриваемое состояние

Клиент хранит два независимых состояния игры:

- `liveState` и `liveVersion` — последнее подтверждённое сервером состояние;
- `viewedState` и `historyCursor` — локально выбранная точка истории, которую
  сейчас показывает игровое поле;
- очередь воспроизведения и необязательный текущий анимационный переход между
  двумя состояниями.

Новые `game:events` всегда применяются к `liveState`, даже когда игрок
просматривает прошлое. Они добавляются в историю, но не сдвигают выбранный
`historyCursor`. Если концом воспроизведения выбрано «текущее состояние», при
запуске диапазон фиксируется на конкретной `liveVersion`, чтобы новые ходы не
меняли проигрываемый отрезок.

Игровое поле показывает `viewedState`, когда курсор находится в прошлом, и
`liveState` — сразу после возврата к текущему состоянию. Во время локального
воспроизведения оно показывает переход от `beforeState` к `afterState`.
Интерфейс явно сообщает, что игрок смотрит историю, и показывает действие для
быстрого возврата в live.

Доступные команды, их проверка на клиенте и `expectedVersion` всегда
вычисляются только из `liveState` и `liveVersion`. Просмотр прошлого не меняет
ход игры и не позволяет отправить команду относительно исторической версии.

## Синхронизация состояния

При первом подключении клиент получает полный `game:snapshot`. Это сообщение
формируется из актуального состояния `ActiveGame` или из состояния,
восстановленного сервером по событиям; отдельно такой снимок на сервере не
хранится. Для ленты ходов клиент отдельно загружает доступную текущему
пользователю цепочку событий через `GET /api/games/:gameId/events`. Затем новые
`game:events` дополняют эту цепочку в реальном времени.

Клиент хранит:

- идентификатор игры;
- актуальную версию и безопасное `liveState`;
- безопасные события, сгруппированные по командам;
- локальные `viewedState` и `historyCursor`;
- выбранный диапазон и состояние воспроизведения;
- очередь команд и текущую необязательную UI-анимацию;
- состояние соединения;
- ожидающие подтверждения команды.

История из HTTP и события Socket.IO объединяются по sequence number, поэтому
гонка между их загрузкой не создаёт дубликатов. Если пришло событие не следующей
версии или восстановить соединение не удалось, клиент запрашивает новый
snapshot и недостающую часть истории.

## Feature flags и dev-панель

При инициализации приложения клиент вызывает:

```text
GET /api/config/feature-flags.json
```

Этот snapshot хранится в Zustand и управляет общим UI и разделами вне активной партии. Он не обновляется в фоне.

Feature flags фиксируются в `GameCreated` и входят в каждый полный игровой
snapshot. Клиент получает их уже при создании игры или первом подключении к ней
и хранит отдельно в контексте текущей игры.

Клиент не использует initialization snapshot для игровой механики. После
reconnect он получает актуальное состояние игры с теми же feature flags,
которые были записаны в `GameCreated`.

В development-сборке переключатель real/fake backend находится внутри `/login`
до входа, а после входа доступен в dev-панели по кнопке `Dev` в навигации. Выбор
сохраняется через Zustand `persist` в `localStorage`.

Локальные overrides игровых флагов в Zustand не используем. В fake-режиме
панель изменяет snapshot флагов выбранной игры в IndexedDB через
`DevelopmentApi`, после чего fake backend пересобирает состояние и синхронизирует
вкладки. В real-режиме игровые флаги в панели доступны только для чтения.

## Критерии готовности

- две вкладки могут войти в одну игру как разные игроки;
- клиентский код разделён по слоям FSD и соблюдает направление зависимостей;
- переключатель backend доступен на `/login` и в dev-панели после входа;
- выбор real/fake backend переживает reload;
- страницы используют единые API-контракты и не знают о выбранном backend;
- две вкладки могут играть разными fake-пользователями через один SharedWorker;
- fake-данные сохраняются в IndexedDB через `idb`;
- fake backend и fake database отсутствуют в production bundle;
- Google, Telegram и Yandex входят в три отдельных fake-аккаунта;
- fake login не обращается к внешним OAuth-провайдерам;
- пользователь может войти через Google, Telegram или Yandex ID;
- аватары всех провайдеров загружаются только с домена War Chest;
- отсутствие аватара показывает локальную заглушку;
- профиль текущего пользователя и профиль другого игрока используют один экран;
- профиль показывает завершённые игры пользователя от новых к старым;
- наблюдение за игрой не добавляет её в историю игрока;
- запись истории открывает страницу просмотра завершённой игры;
- на странице игры видна сгруппированная по командам история ходов;
- игрок может переходить по истории назад и вперёд;
- игрок может воспроизвести отрезок между двумя командами или до live-состояния;
- анимируемое событие завершается до перехода к следующей команде;
- команда без анимируемых событий применяется без ожидания;
- отмена анимации приводит к корректному состоянию выбранной точки истории;
- новые события обновляют live-состояние, не сбрасывая локальную точку просмотра;
- доступные действия и `expectedVersion` не зависят от точки просмотра истории;
- возврат в live показывает последнее подтверждённое состояние;
- зритель в реальном времени видит только общедоступное состояние;
- клиент загружает application flags во время инициализации;
- клиент получает feature flags из `GameCreated` или snapshot;
- в real-режиме клиент не меняет базовые значения флагов во время партии;
