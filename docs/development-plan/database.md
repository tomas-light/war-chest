# База данных в Docker

PostgreSQL хранит пользователей, игры, участников и подтверждённые игровые события. Docker нужен, чтобы каждый разработчик запускал одинаковую локальную базу одной командой.

На первом этапе в Docker запускаем только базу. Сервер и клиент удобнее запускать локально с быстрым обновлением кода.

## Настройка окружения

В корне проекта понадобятся:

```text
compose.yaml
.env.example
```

В `compose.yaml` настраиваем:

- PostgreSQL с закреплённой версией образа;
- постоянный volume;
- healthcheck;
- локальный порт;
- имя базы, пользователя и пароль из переменных окружения.

Секреты не добавляем в Git. В `.env.example` оставляем только безопасный пример конфигурации.

## Схема данных

Минимальный набор таблиц:

### `users`

Идентичность пользователя, необходимая для участия в играх и просмотра личной истории.

### `user_identities`

Связывает пользователя с внешним провайдером Google или Telegram. Постоянным ключом служит пара `provider` и `provider_subject`.

### `auth_sessions`

Хранит серверные сессии War Chest, их срок действия и отзыв. В базе сохраняется хеш session token, а не значение cookie.

### `games`

Основная запись игры:

- идентификатор;
- статус;
- текущая версия;
- время создания, старта и завершения.

### `game_participants`

Связывает пользователя с игрой:

- роль;
- место игрока;
- итоговый результат;
- время присоединения.

### `game_events`

Последовательный журнал подтверждённых событий:

- идентификатор события;
- игра;
- порядковый номер;
- тип;
- версия формата события;
- JSON-данные;
- время создания.

Событие `GameStarted` хранит полный snapshot feature flags, с которыми была запущена партия. Благодаря этому восстановление и replay не зависят от текущего runtime-файла окружения.

### `game_snapshots`

Производный снимок состояния:

- игра;
- sequence number последнего применённого события;
- версия формата snapshot;
- JSON-состояние;
- время создания.

Для одной игры и sequence number существует не больше одного snapshot. Снимок можно удалить и построить заново, не потеряв игровую историю.

### `processed_commands`

Хранит идентификаторы обработанных команд и защищает от повторного применения хода после reconnect.

## Повтор завершённой партии

Для replay достаточно упорядоченной цепочки `game_events`. Отдельную копию данных для повтора не создаём.

Чтобы цепочка оставалась самодостаточной, события хранят:

- состав участников и места;
- фактические результаты раздачи, перемешивания и других случайных действий;
- публичные и частные игровые изменения;
- feature flags из `GameStarted`;
- версию правил и версию формата события;
- завершение по обычным правилам или по таймауту.

Команда вроде `ShuffleDeck` для replay недостаточна, если результат зависит от случайности. В истории должен находиться уже свершившийся результат, например точный порядок карт или последовательность событий раздачи.

Snapshots не являются частью логической истории replay. Их можно использовать, чтобы быстро перейти к нужному месту, но полная цепочка событий должна воспроизводиться и без них.

## Миграции

Для схемы и миграций используем Drizzle ORM. Нужны команды:

```text
yarn db:generate
yarn db:migrate
yarn db:seed
yarn db:studio
```

Обязательные ограничения:

- уникальный номер события внутри игры;
- уникальный идентификатор команды;
- уникальный snapshot для пары игры и sequence number;
- уникальная пара провайдера и внешнего идентификатора;
- уникальное место игрока внутри игры;
- внешние ключи на пользователей и игры;
- индексы для поиска сессии, истории пользователя и загрузки событий игры.

## Критерии готовности

- `docker compose up -d` запускает здоровую базу;
- миграции применяются к пустой базе;
- повторный запуск миграций ничего не ломает;
- тестовые данные можно создать отдельной командой;
- сервер проверяет соединение при старте;
- удаление контейнера не удаляет данные из volume.
