# База данных в Docker

PostgreSQL хранит пользователей, игры, участников и подтверждённые игровые события. Docker нужен, чтобы каждый разработчик запускал одинаковую локальную базу одной командой.

На первом этапе в Docker запускаем только базу. Сервер и клиент удобнее запускать локально с быстрым обновлением кода.

Работу с PostgreSQL выделяем в workspace-пакет `packages/database`. Так описание
таблиц и история миграций не зависят от структуры Fastify-приложения, а сервер
подключает их через одну явную зависимость `@war-chest/database`.

## Пакет `packages/database`

Предлагаемая структура:

```text
packages/database/
  env.yaml               общая конфигурация подключения
  env.local.yaml         локальные переопределения, не входит в Git
  migrations/            сгенерированные SQL-миграции
  src/
    schema/
      auth.ts
      games.ts
      index.ts
    client.ts             создание подключения
    migrate.ts            запуск миграций
    seed.ts               тестовые данные
    index.ts              публичный API пакета
  drizzle.config.ts
  package.json
  tsconfig.json
```

Пакет отвечает за:

- Drizzle-схему таблиц, индексов, связей и ограничений;
- создание клиента PostgreSQL и управление транзакциями;
- генерацию и применение версионируемых SQL-миграций;
- seed-данные и технические утилиты для тестовой базы;
- загрузку собственной плоской конфигурации;
- экспорт типов схемы и низкоуровневого доступа к данным.

`packages/database` не знает о Fastify, Socket.IO и правилах игры. Репозитории,
которые реализуют сценарии приложения, например загрузку игры и атомарное
сохранение игровых событий, остаются рядом с соответствующим модулем в
`apps/server`. Они используют клиент, транзакции и схему из
`@war-chest/database`.

Пакет читает `packages/database/env.yaml` и необязательный
`packages/database/env.local.yaml` самостоятельно. Явно переданные переменные
процесса имеют наивысший приоритет. Этот загрузчик используют и серверное
подключение, и команды миграции, seed и Drizzle Studio, поэтому параметры базы
не дублируются в `apps/server`.

## Настройка окружения

В корне проекта понадобятся:

```text
compose.yaml
.env.example
```

В `compose.yaml` настраиваем:

- PostgreSQL с закреплённой версией образа;
- постоянный volume;
- healthcheck;
- локальный порт;
- имя базы, пользователя и пароль из переменных окружения.

Секреты не добавляем в Git. В `.env.example` оставляем только безопасный пример конфигурации.

`.env.example` относится только к переменным, которые Docker Compose использует
при создании контейнера PostgreSQL. Приложение и инструменты Drizzle получают
параметры подключения из `packages/database/env.yaml`, локального
переопределения и явно переданных переменных процесса.

## Схема данных

Минимальный набор таблиц:

### `users`

Идентичность пользователя, необходимая для участия в играх и публичного профиля
игрока. Профиль другого пользователя получает только безопасные поля из этой
таблицы и версию аватара; внешние идентичности хранятся отдельно и не
публикуются.

### `user_avatars`

Хранит локальную копию аватара отдельно от часто читаемой строки пользователя:

- `user_id` — первичный и внешний ключ на `users`;
- `content` — бинарные данные PostgreSQL `bytea`, не base64;
- `content_type` — MIME type нормализованного изображения;
- `content_hash` — hash для обнаружения изменений и версии URL;
- `updated_at` — время последнего успешного обновления.

Внешний URL провайдера не сохраняем. Пакет авторизации загружает изображение при
входе пользователя, нормализует его и заменяет строку `user_avatars` только
после успешной обработки. Ошибка загрузки не удаляет предыдущую версию.

### `user_identities`

Связывает пользователя с внешним провайдером Google, Telegram или Yandex ID.
Постоянным ключом служит пара `provider` и `provider_subject`.

### `auth_sessions`

Хранит серверные сессии War Chest, их срок действия и отзыв. В базе сохраняется хеш session token, а не значение cookie.

### `games`

Основная запись игры:

- идентификатор;
- статус;
- текущая версия;
- время создания, старта и завершения.

### `game_participants`

Связывает пользователя с игрой:

- роль;
- место игрока;
- итоговый результат.

Время присоединения отдельно в `game_participants` не храним. Оно уже зафиксировано в событии `PlayerJoined`, поэтому дублировать его в таблице участников нет необходимости.

История в профиле строится по `game_participants` и `games`: выбираем
завершённые партии, где пользователь участвовал как игрок, и сортируем их по
времени завершения. Участие только в роли зрителя в этот список не входит.

### `game_events`

Последовательный журнал подтверждённых событий:

- идентификатор события;
- игра;
- необязательный идентификатор команды-причины;
- порядковый номер;
- тип;
- версия формата события;
- JSON-данные;
- время создания.

Событие `GameCreated` хранит полный snapshot feature flags, с которыми была
создана игра. Благодаря этому ожидание участников, старт партии, восстановление
и replay не зависят от текущего runtime-файла окружения.

Все события, созданные одной принятой командой игрока, ссылаются на один
`command_id`. Системные события, которые возникают без команды игрока, хранят
`NULL`. Связь нужна только для группировки истории: источником состояния
по-прежнему остаётся последовательность событий.

### `processed_commands`

Хранит метаданные принятых команд:

- идентификатор команды и игру;
- пользователя, отправившего команду;
- тип команды без исходного payload;
- время обработки.

Запись защищает от повторного применения хода после reconnect и объединяет
созданные командой события в один элемент истории. Исходный payload команды не
храним: для восстановления состояния достаточно подтверждённых событий.

## Повтор завершённой партии

Для replay достаточно упорядоченной цепочки `game_events`. Отдельную копию данных для повтора не создаём.

Чтобы цепочка оставалась самодостаточной, события хранят:

- состав участников и места;
- фактические результаты раздачи, перемешивания и других случайных действий;
- публичные и частные игровые изменения;
- feature flags из `GameCreated`;
- версию правил и версию формата события;
- завершение по обычным правилам или по таймауту.

Команда вроде `ShuffleDeck` для replay недостаточна, если результат зависит от случайности. В истории должен находиться уже свершившийся результат, например точный порядок карт или последовательность событий раздачи.

Отдельные копии `GameState` не сохраняем ни в PostgreSQL, ни рядом с активной
игрой. Пока игра активна, сервер использует её актуальное состояние из
`ActiveGame`. После перезапуска, выгрузки из памяти или при просмотре истории
состояние восстанавливается из полной цепочки событий.

## Миграции

Для схемы и миграций используем Drizzle ORM. Команды объявляем в
`packages/database/package.json`, а из корневого `package.json` добавляем
короткие прокси для повседневной работы:

```text
yarn db:generate
yarn db:migrate
yarn db:seed
yarn db:studio
```

Эквивалентный прямой вызов пакета:

```text
yarn workspace @war-chest/database db:migrate
```

Сгенерированные SQL-миграции храним в `packages/database/migrations` и добавляем
в Git. Изменение схемы и соответствующая миграция должны попадать в один набор
изменений.

Обязательные ограничения:

- уникальный номер события внутри игры;
- уникальный идентификатор команды;
- уникальная пара провайдера и внешнего идентификатора;
- не больше одного аватара на пользователя;
- уникальное место игрока внутри игры;
- не больше одного участия пользователя в одной игре;
- внешний ключ `game_events.command_id` на принятую команду;
- внешние ключи на пользователей и игры;
- индексы для поиска сессии, истории пользователя и загрузки событий игры.

## Критерии готовности

- `docker compose up -d` запускает здоровую базу;
- миграции применяются к пустой базе;
- повторный запуск миграций ничего не ломает;
- тестовые данные можно создать отдельной командой;
- аватары сохраняются как бинарные данные в отдельной таблице;
- схема и миграции находятся в `packages/database`;
- пакет базы читает собственные `env.yaml` и необязательный `env.local.yaml`;
- сервер и команды Drizzle используют один загрузчик конфигурации базы;
- сервер подключает `@war-chest/database` как workspace-зависимость;
- пакет базы не зависит от `apps/server` и `game-engine`;
- сервер проверяет соединение при старте;
- удаление контейнера не удаляет данные из volume.
