# Сервер

Сервер — авторитетный участник игры. Он принимает команды, проверяет их через `game-engine`, сохраняет получившиеся события и только после этого рассылает обновления игрокам и зрителям.

HTTP используем для обычных операций, а Socket.IO — для активной игровой сессии.

## Предлагаемая структура

```text
apps/server/src/
  config/
    load-config.ts
    schema.ts
  feature-flags/
    feature-flags.service.ts
  auth/
    auth.routes.ts
  games/
    game.repository.ts
    game.service.ts
    game.routes.ts
    game.socket.ts
    active-games.ts
  app.ts
  index.ts
```

Схема PostgreSQL, клиент и миграции находятся в `packages/database`. Сервер
подключает `@war-chest/database` как workspace-зависимость. При создании клиента
пакет сам читает `packages/database/env.yaml`, необязательный локальный файл и
явно переданные переменные процесса. `DATABASE_URL` в конфигурации сервера не
дублируется.

`game.repository.ts` остаётся на сервере: он описывает нужные игровому сценарию
запросы и границы транзакций, но выполняет их через схему и клиент пакета базы.

Интеграции с Google, Telegram и Yandex ID, а также сессии War Chest находятся в
`packages/auth`. Серверный `auth.routes.ts` остаётся тонким HTTP-адаптером над
публичным API `@war-chest/auth`.

## HTTP API

Минимальный набор маршрутов:

```text
GET  /health

POST /auth/google
GET  /auth/telegram/start
GET  /auth/telegram/callback
GET  /auth/yandex/start
GET  /auth/yandex/callback
GET  /auth/session
POST /auth/logout
GET  /users/:userId/avatar

GET  /config/feature-flags.json

POST /games
GET  /games/:gameId
POST /games/:gameId/join
POST /games/:gameId/start
GET  /me/games
GET  /games/:gameId/events
```

Подробная схема входа через Google, Telegram и Yandex ID описана в разделе
[«Авторизация»](./authentication.md).

`GET /users/:userId/avatar` читает сохранённое изображение из
`packages/database` и требует сессию War Chest. Клиент добавляет `contentHash` в
query-параметр версии, а сервер разрешает долго хранить ответ в браузерном кэше:
`Cache-Control: private, max-age=31536000, immutable`. После изменения аватара
меняется URL, поэтому отдельный механизм проверки версии ответа не нужен.

Сервер читает свой `env.yaml` и локальные переопределения до создания
HTTP-приложения, затем инициализирует `@war-chest/database` с конфигурацией его
собственной границы и `@war-chest/auth` с конфигурацией авторизации. При ошибке
любой из конфигураций сервер не начинает принимать запросы.

Feature flags живут в отдельном runtime-файле активного окружения. Сервер не следит за его изменениями в фоне.

`GET /config/feature-flags.json` читает файл для инициализации общего клиентского UI. При старте новой игры сервер читает файл ещё раз, а полный snapshot записывает в событие `GameStarted`.

После старта сервер использует `featureFlags` из состояния конкретной игры. Замена runtime-файла не влияет на уже идущие партии и применяется только при следующем старте.

## Socket.IO

Каждая игра получает комнату:

```text
game:<gameId>
```

Сообщения клиента:

```text
game:join
game:leave
game:command
game:sync
```

Сообщения сервера:

```text
game:snapshot
game:events
game:presence
game:error
```

## Обработка команды

Сервер должен:

1. Проверить пользователя, участие в игре и роль.
2. Загрузить активную игру или восстановить её из событий.
3. Сравнить `expectedVersion` с текущей версией.
4. Передать команду в `game-engine`.
5. Получить новые события.
6. Сохранить события и идентификатор команды в одной транзакции.
7. Применить события к состоянию в памяти.
8. Сформировать безопасное представление для каждого получателя.
9. Разослать обновление и подтвердить команду.

Для одной игры команды обрабатываются последовательно. `commandId` защищает от повторного хода, а `expectedVersion` — от конфликтующих вкладок и рассинхронизации.

## Активные игры

Один серверный процесс может держать активные игры в памяти:

```ts
interface ActiveGame {
  state: GameState;
  version: number;
  featureFlags: FeatureFlags;
  connectedPlayers: Set<string>;
  connectedSpectators: Set<string>;
}
```

Пока игра находится в памяти, `state` содержит её единственное актуальное
внутреннее состояние. Сервер не хранит рядом с ним копии предыдущих состояний.

Если игры нет в памяти, сервер читает её события по порядку и восстанавливает
состояние через `applyEvent`. Для продолжающейся игры восстановленное состояние
становится новым `ActiveGame`. При просмотре завершённой игры его можно
использовать только в рамках запроса, не добавляя игру в набор активных.

После периода неактивности `ActiveGame` можно удалить: постоянная история уже
находится в PostgreSQL.

При восстановлении `featureFlags` берутся из `GameStarted`, а не из текущего runtime-файла.

## Отключение игрока

Игрок считается отключённым, когда у него не остаётся ни одного активного Socket.IO-соединения с игрой.

Сервер читает `DISCONNECTED_PLAYER_TIMEOUT_MINUTES` из конфигурации, вычисляет точный `reconnectDeadline` и сохраняет его в событии `PlayerDisconnected`. Если игрок возвращается вовремя, сервер записывает `PlayerReconnected` и отменяет таймер.

После истечения срока сервер в транзакции проверяет, что игрок всё ещё отключён, и записывает:

```json
{
  "type": "PlayerDefeated",
  "payload": {
    "playerId": "player-42",
    "reason": "disconnectTimeout"
  }
}
```

Игроку засчитывается поражение, и он больше не участвует в очереди ходов. Если после этого выполнено условие завершения партии, движок дополнительно создаёт `GameFinished`.

Сохранённый `reconnectDeadline` позволяет восстановить таймер после перезапуска сервера. Повторная обработка того же срока не должна создавать второе поражение.

## Получение актуального состояния

Сообщение `game:snapshot` — это формат полной синхронизации клиента, а не
отдельный сохранённый снимок на сервере.

Когда клиент подключается или сообщает о рассинхронизации, сервер:

1. Берёт актуальные `state` и `version` из `ActiveGame`, если игра находится в
   памяти.
2. Если `ActiveGame` отсутствует, читает полную цепочку событий и
   последовательно применяет её к начальному состоянию.
3. Формирует из полученного состояния безопасное представление для конкретного
   игрока или зрителя.
4. Отправляет представление и его версию в `game:snapshot`.

Тот же способ используется при просмотре игры в истории. Replay по-прежнему
строится по событиям, поэтому отдельные копии `GameState` не нужны ни в памяти,
ни в PostgreSQL.

## Зрители

Зрители получают обновления в реальном времени, без задержки. Для них сервер формирует только общедоступное представление поля:

- открытые элементы поля;
- текущий ход и общие счётчики;
- публичные действия игроков;
- статус участников.

Частная рука, секретные цели и адресованные конкретному игроку данные не входят
ни в представление состояния, ни в события зрителя. Зритель не может отправлять
игровые команды.

## Критерии готовности

- сервер запускается только с валидной конфигурацией;
- сервер использует конфигурацию подключения из `packages/database`;
- OAuth-маршруты используют реализацию и конфигурацию из `packages/auth`;
- аватары отдаются с домена War Chest и не ссылаются на внешних провайдеров;
- сервер читает runtime-файл при старте новой игры;
- сервер отдаёт актуальный runtime-файл при инициализации клиента;
- сервер не валидирует схему и состав feature-flags JSON;
- `GameStarted` содержит полный snapshot флагов;
- команды используют флаги текущей игры, а не актуальный runtime-файл;
- замена runtime-файла не меняет начатые игры;
- `/health` проверяет готовность приложения и базы;
- Socket.IO проверяет собственную сессию War Chest;
- зритель не может отправить игровой ход;
- зритель получает общедоступные события без задержки;
- reconnect deadline вычисляется из конфигурации;
- истечение reconnect deadline создаёт одно поражение;
- таймер отключения восстанавливается после перезапуска;
- полная синхронизация использует актуальное состояние из `ActiveGame`;
- при отсутствии `ActiveGame` состояние собирается из полной истории;
- просмотр игры в истории не зависит от наличия состояния в памяти;
- после перезапуска состояние собирается из полной истории;
- повторный `commandId` не изменяет игру второй раз;
- конфликт версии возвращает клиенту понятную ошибку;
- событие рассылается только после успешного сохранения;
- игра восстанавливается после перезапуска процесса.
