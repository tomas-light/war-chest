# Сервер

Сервер — авторитетный участник игры. Он принимает команды, проверяет их через `game-engine`, сохраняет получившиеся события и только после этого рассылает обновления игрокам и зрителям.

HTTP используем для обычных операций, а Socket.IO — для активной игровой сессии.
Все серверные HTTP-маршруты находятся под `/api`, Socket.IO использует путь
`/api/socket.io`. В production тот же Fastify-процесс может раздавать сборку
клиента и возвращать `index.html` для SPA deep links.

## Статус реализации

- [x] bootstrap Fastify, конфигурация и обязательная проверка PostgreSQL;
- [x] `/api/health`, OAuth, session, logout и user endpoints;
- [x] Socket.IO authentication, Zod-валидация сообщений и игровые комнаты;
- [x] опциональная раздача production SPA и deep-link fallback;
- [x] HTTP adapters Google, Telegram и Yandex OAuth;
- [x] runtime feature-flags reader и endpoint;
- [ ] игровые HTTP endpoints и game service;
- [ ] выполнение, транзакционное сохранение и рассылка команд;
- [ ] ActiveGame, reconnect deadline и восстановление после перезапуска.

Точные доступные сейчас endpoints и ограничения transport scaffold описаны в
[фактической документации server](../server/README.md).

Автономные постановки следующих работ находятся в разделе
[«Реализация игрового server: этапы 4–8»](./server-implementation/README.md).
Их следует использовать для передачи каждого этапа без контекста обсуждения.

## Предлагаемая структура

```text
apps/server/src/
  config/
    loadServerConfig.ts
    schema.ts
  featureFlags/
    FeatureFlagsService.ts
    registerFeatureFlagsRoutes.ts
  auth/
    registerAuthRoutes.ts
    registerAuthSession.ts
  users/
    PublicUser.ts
    UserRepository.ts
    registerUserRoutes.ts
  games/
    ActiveGames.ts
    GameRepository.ts
    GameService.ts
    registerGameRoutes.ts
    registerGameSocket.ts
  socket/
    createSocketServer.ts
  createApp.ts
  index.ts
  startServer.ts
```

Схема PostgreSQL, клиент и миграции находятся в `packages/database`. Сервер
подключает `@war-chest/database` как workspace-зависимость. При создании клиента
пакет сам читает `packages/database/env.yaml`, необязательный локальный файл и
явно переданные переменные процесса. `DATABASE_URL` в конфигурации сервера не
дублируется.

`GameRepository.ts` и `UserRepository.ts` остаются на сервере: они описывают
нужные HTTP-сценариям запросы и границы транзакций, но выполняют их через схему
и клиент пакета базы.

Интеграции с Google, Telegram и Yandex ID, а также сессии War Chest находятся в
`packages/auth`. Серверный `registerAuthRoutes.ts` остаётся тонким HTTP-адаптером над
публичным API `@war-chest/auth`.

## HTTP API

Минимальный набор маршрутов:

```text
GET  /api/health

POST /api/auth/google
GET  /api/auth/telegram/start
GET  /api/auth/telegram/callback
GET  /api/auth/yandex/start
GET  /api/auth/yandex/callback
GET  /api/auth/session
POST /api/auth/logout
GET  /api/users/:userId
GET  /api/users/:userId/avatar
GET  /api/users/:userId/games

GET  /api/config/feature-flags.json

POST /api/games
GET  /api/games/:gameId
POST /api/games/:gameId/join
POST /api/games/:gameId/start
GET  /api/games/:gameId/events
```

`GET /api/auth/session` читает cookie с именем из конфигурации `packages/auth` и
проверяет её через `auth.getSession()`. Действующая сессия возвращается в
transport-формате с ISO-датой:

```json
{
  "expiresAt": "2026-09-03T10:00:00.000Z",
  "user": {
    "id": "user-1",
    "displayName": "Ada",
    "avatarVersion": "avatar-hash"
  }
}
```

Отсутствующая, истёкшая, отозванная или неизвестная сессия получает одинаковый
ответ `401 unauthorized`, чтобы HTTP-слой не раскрывал причину отказа. Успешные
ответы и ошибки этого маршрута отправляются с `Cache-Control: no-store`.

`POST /api/auth/logout` безопасен при повторном вызове и при отсутствии session
cookie. Адаптер передаёт token в `auth.logout()`, переносит все возвращённые
пакетом атрибуты очищающей cookie в ответ и завершает запрос статусом `204`.
Ответ logout также не кэшируется.

Тот же адаптер предоставляет Fastify pre-handler `requireAuthSession` для
защищённых HTTP-маршрутов. Он выполняет проверку один раз и сохраняет найденную
`AuthSession` в текущем request, поэтому обработчики профилей и игр не читают
cookie и не обращаются к `@war-chest/auth` повторно.

`POST /api/games/:gameId/join` принимает выбранную пользователем позицию:

```json
{
  "team": "white",
  "seat": 1
}
```

Сервер передаёт `team` и `seat` в `JoinGame` только вместе; движок отклоняет
неизвестную или уже занятую позицию. Повторный join того же пользователя
возвращает существующее участие и не позволяет сменить позицию через второй
запрос.

Подробная схема входа через Google, Telegram и Yandex ID описана в разделе
[«Авторизация»](./authentication.md).

Профильные маршруты используют общий `requireAuthSession`. Поэтому профиль,
аватар и история доступны только пользователям с действующей сессией, но могут
показывать как текущего пользователя, так и другого игрока.

`GET /api/users/:userId/avatar` читает сохранённое изображение через
`auth.getAvatar()`. Клиент добавляет `avatarVersion` в query-параметр версии, а
сервер разрешает долго хранить ответ в браузерном кэше:
`Cache-Control: private, max-age=31536000, immutable`. После изменения аватара
меняется URL, поэтому отдельный механизм проверки версии ответа не нужен.
Если сохранённого изображения нет, endpoint возвращает `404 avatar_not_found`.

`GET /api/users/:userId` возвращает публичную часть профиля: идентификатор,
отображаемое имя и версию аватара. Внешние идентичности и данные
OAuth-провайдеров в ответ не входят.

```json
{
  "id": "10000000-0000-4000-8000-000000000001",
  "displayName": "Ada",
  "avatarVersion": "avatar-hash"
}
```

`GET /api/users/:userId/games` возвращает завершённые игры, в которых пользователь
участвовал с ролью игрока. Игры, где пользователь был только зрителем, в список
не входят. Результаты сортируются по времени завершения от новых к старым и
отдаются страницами:

```text
GET /api/users/:userId/games?cursor=<cursor>&limit=20
```

По умолчанию endpoint возвращает 20 игр, допустимый `limit` находится в
диапазоне от 1 до 100. Непрозрачный Base64url cursor содержит пару
`finishedAt + gameId`: дополнительный идентификатор сохраняет стабильный
порядок, если несколько партий завершились одновременно.

Каждый элемент содержит данные, необходимые карточке истории: идентификатор и
время завершения игры, участников, команду выбранного пользователя и победившую
команду. Результат `victory` или `defeat` вычисляется сравнением этих команд.
Участник содержит публичный профиль и выбранную позицию, но не внешнюю
идентичность OAuth.

```json
{
  "items": [
    {
      "id": "20000000-0000-4000-8000-000000000001",
      "finishedAt": "2026-08-04T10:00:00.000Z",
      "team": "white",
      "winnerTeam": "white",
      "result": "victory",
      "participants": [
        {
          "id": "10000000-0000-4000-8000-000000000001",
          "displayName": "Ada",
          "avatarVersion": "avatar-hash",
          "team": "white",
          "seat": 1
        }
      ]
    }
  ],
  "nextCursor": null
}
```

Неизвестный пользователь получает `404 user_not_found`. Некорректные UUID,
limit и cursor отклоняются до запроса истории.

`GET /api/games/:gameId/events` возвращает упорядоченную цепочку событий для
истории ходов и replay. Endpoint поддерживает загрузку по sequence number:

```text
GET /api/games/:gameId/events?afterSequence=0&limit=500
```

Ответ содержит sequence number и версию каждого события, а также безопасные
метаданные команды, которая стала его причиной: `commandId`, игрока и доступное
получателю описание действия. Несколько событий с одним `commandId` образуют
одну запись в истории ходов. Для серверных событий без команды `commandId`
отсутствует. Исходный тип или описание скрытой команды заменяется нейтральной
записью и не раскрывает её содержание.

Сервер формирует события для конкретного получателя так же, как при доставке
через Socket.IO. Игрок получает только общие данные и собственную частную
информацию, зритель — только общедоступные изменения. Исходные payload команд и
чужие скрытые данные endpoint не возвращает.

Sequence number не пропускается даже тогда, когда внутреннее событие полностью
скрыто от получателя. В таком случае сервер возвращает нейтральный
`ViewSequenceAdvanced` без игровых данных. Он обновляет `lastEventSequence`
представления, но не изменяет видимое состояние и не раскрывает тип скрытого
события.

Сервер читает свой `env.yaml` и локальные переопределения до создания
HTTP-приложения, затем инициализирует `@war-chest/database` с конфигурацией его
собственной границы и `@war-chest/auth` с конфигурацией авторизации. При ошибке
любой из конфигураций сервер не начинает принимать запросы.

Feature flags живут в отдельном runtime-файле активного окружения. Сервер не следит за его изменениями в фоне.

`GET /api/config/feature-flags.json` читает файл для инициализации общего
клиентского UI. Создание игры независимо читает тот же runtime-файл ещё раз.

При обработке `POST /api/games` сервер независимо читает runtime-файл, добавляет
полученные значения в доверенную команду `CreateGame` и записывает полный
snapshot в событие `GameCreated`. Клиент не передаёт игровые feature flags в
запросе создания.

После создания сервер использует `featureFlags` из состояния конкретной игры.
Команда старта партии не перечитывает runtime-файл. Его замена не влияет на уже
созданные игры и применяется только при создании следующей игры.

## Socket.IO

Каждая игра получает комнату:

```text
game:<gameId>
```

Сообщения клиента:

```text
game:join
game:leave
game:command
game:sync
```

Сообщения сервера:

```text
game:snapshot
game:events
game:presence
game:error
```

## Обработка команды

Сервер должен:

1. Проверить пользователя, участие в игре и роль.
2. Загрузить активную игру или восстановить её из событий.
3. Сравнить `expectedVersion` с текущей версией.
4. Передать команду в `game-engine`.
5. Получить новые события.
6. Сохранить события и метаданные команды в одной транзакции.
7. Применить события к состоянию в памяти.
8. Сформировать безопасное представление для каждого получателя.
9. Разослать обновление и подтвердить команду.

Для одной игры команды обрабатываются последовательно. `commandId` защищает от повторного хода, а `expectedVersion` — от конфликтующих вкладок и рассинхронизации.

Каждое созданное командой событие связывается с её `commandId`. Это позволяет
клиенту показать одно действие игрока как единый элемент истории, даже если
движок создал для него несколько событий.

Один пользователь может иметь только одно участие в игре и не может занять две
позиции через разные вкладки или соединения. Повторный join с той же сессией
возвращает существующее участие и не создаёт второго игрока. Партия начинается
только между разными пользователями.

## Активные игры

Один серверный процесс может держать активные игры в памяти:

```ts
interface ActiveGame {
  state: GameState;
  version: number;
  featureFlags: FeatureFlags;
  connectedPlayers: Set<string>;
  connectedSpectators: Set<string>;
}
```

Пока игра находится в памяти, `state` содержит её единственное актуальное
внутреннее состояние. Сервер не хранит рядом с ним копии предыдущих состояний.

Если игры нет в памяти, сервер читает её события по порядку и восстанавливает
состояние через `applyEvent`. Для продолжающейся игры восстановленное состояние
становится новым `ActiveGame`. При просмотре завершённой игры его можно
использовать только в рамках запроса, не добавляя игру в набор активных.

После периода неактивности `ActiveGame` можно удалить: постоянная история уже
находится в PostgreSQL.

При восстановлении `featureFlags` берутся из `GameCreated`, а не из текущего runtime-файла.

## Отключение игрока

Игрок считается отключённым, когда у него не остаётся ни одного активного Socket.IO-соединения с игрой.

Сервер читает `DISCONNECTED_PLAYER_TIMEOUT_MINUTES` из конфигурации, вычисляет точный `reconnectDeadline` и сохраняет его в событии `PlayerDisconnected`. Если игрок возвращается вовремя, сервер записывает `PlayerReconnected` и отменяет таймер.

После истечения срока сервер в транзакции проверяет, что игрок всё ещё отключён, и записывает:

```json
{
  "type": "PlayerDefeated",
  "payload": {
    "playerId": "player-42",
    "reason": "disconnectTimeout"
  }
}
```

Игроку засчитывается поражение, и он больше не участвует в очереди ходов. Если после этого выполнено условие завершения партии, движок дополнительно создаёт `GameFinished`.

Сохранённый `reconnectDeadline` позволяет восстановить таймер после перезапуска сервера. Повторная обработка того же срока не должна создавать второе поражение.

## Получение актуального состояния

Сообщение `game:snapshot` — это формат полной синхронизации клиента, а не
отдельный сохранённый снимок на сервере.

Когда клиент подключается или сообщает о рассинхронизации, сервер:

1. Берёт актуальные `state` и `lastEventSequence` из `ActiveGame`, если игра
   находится в памяти.
2. Если `ActiveGame` отсутствует, читает полную цепочку событий и
   последовательно применяет её к начальному состоянию.
3. Формирует из полученного состояния безопасное представление для конкретного
   игрока или зрителя.
4. Отправляет представление и его `lastEventSequence` в `game:snapshot`.

Тот же способ используется при просмотре игры в истории. Replay по-прежнему
строится по событиям, поэтому отдельные копии `GameState` не нужны ни в памяти,
ни в PostgreSQL.

## Зрители

Зрители получают обновления в реальном времени, без задержки. Для них сервер формирует только общедоступное представление поля:

- открытые элементы поля;
- текущий ход и общие счётчики;
- публичные действия игроков;
- статус участников.

Частная рука, секретные цели и адресованные конкретному игроку данные не входят
ни в представление состояния, ни в события зрителя. Зритель не может отправлять
игровые команды.

## Критерии готовности

- сервер запускается только с валидной конфигурацией;
- сервер использует конфигурацию подключения из `packages/database`;
- OAuth-маршруты используют реализацию и конфигурацию из `packages/auth`;
- аватары отдаются с домена War Chest и не ссылаются на внешних провайдеров;
- публичный профиль не раскрывает внешние идентичности пользователя;
- история профиля содержит только завершённые игры пользователя как игрока;
- история профиля поддерживает постраничную загрузку от новых игр к старым;
- история ходов сохраняет порядок событий и группировку по командам;
- HTTP-история и события Socket.IO проходят одинаковую фильтрацию скрытых данных;
- сервер читает runtime-файл при создании новой игры;
- сервер отдаёт актуальный runtime-файл при инициализации клиента;
- сервер проверяет JSON-объект и boolean-тип каждого feature flag, но не знает
  список ключей и не проверяет полноту набора;
- `GameCreated` содержит полный snapshot флагов;
- старт партии не перечитывает runtime-файл;
- команды используют флаги текущей игры, а не актуальный runtime-файл;
- замена runtime-файла не меняет уже созданные игры;
- `/api/health` проверяет готовность приложения и базы;
- Socket.IO проверяет собственную сессию War Chest;
- один пользователь не может занять два места в одной игре;
- зритель не может отправить игровой ход;
- зритель получает общедоступные события без задержки;
- reconnect deadline вычисляется из конфигурации;
- истечение reconnect deadline создаёт одно поражение;
- таймер отключения восстанавливается после перезапуска;
- полная синхронизация использует актуальное состояние из `ActiveGame`;
- при отсутствии `ActiveGame` состояние собирается из полной истории;
- просмотр игры в истории не зависит от наличия состояния в памяти;
- после перезапуска состояние собирается из полной истории;
- повторный `commandId` не изменяет игру второй раз;
- конфликт версии возвращает клиенту понятную ошибку;
- событие рассылается только после успешного сохранения;
- игра восстанавливается после перезапуска процесса.
