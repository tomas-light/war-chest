# Сквозной сценарий и качество

Первый сквозной сценарий проверяет всю архитектуру целиком. Он важнее полной реализации правил: если данные надёжно проходят от клиента через сервер в базу и обратно, механику можно развивать постепенно.

## Первый рабочий сценарий

1. Пользователь входит в приложение.
2. Создаёт игру.
3. Второй пользователь присоединяется из другой вкладки.
4. Первый игрок запускает партию.
5. Игроки по очереди выполняют тестовые ходы.
6. Сервер сохраняет события и рассылает обновления.
7. Зритель подключается и видит публичное состояние.
8. Игрок обновляет страницу и возвращается в игру.
9. Сервер перезапускается и восстанавливает игру из PostgreSQL.
10. Партия завершается и появляется в истории обоих игроков.

## Тестирование

### Игровой движок

- допустимые и запрещённые команды;
- очередность ходов;
- восстановление состояния из событий;
- завершение игры;
- отсутствие скрытых данных в представлениях.

### Сервер

- миграции на чистой базе;
- создание игры и присоединение;
- повторный `commandId`;
- конфликт версий;
- команда от зрителя;
- транзакционное сохранение;
- восстановление после перезапуска.

### Клиент

- получение snapshot;
- последовательное применение событий;
- reconnect;
- рассинхронизация версий;
- отображение ошибок;
- блокировка недоступных действий.

### Сквозные тесты

- два игрока в разных браузерных контекстах;
- игроки и зритель;
- обновление страницы;
- временная потеря соединения;
- перезапуск сервера во время незавершённой партии.

## Команды разработки

В корневом `package.json` должны появиться единые команды:

```text
yarn dev
yarn dev:server
yarn dev:web
yarn db:up
yarn db:down
yarn db:migrate
yarn test
yarn build
```

Локальная разработка:

```text
PostgreSQL  — Docker
Server      — локальный Node.js-процесс
Client      — локальный Vite
```

Контейнеризацию сервера и клиента добавляем после готовности первого сквозного сценария.

## Что не входит в MVP

- Redis;
- Kubernetes;
- микросервисная архитектура;
- брокер сообщений;
- несколько экземпляров Node.js;
- сложный event-sourcing-фреймворк;
- постоянные snapshots до появления реальной проблемы со скоростью восстановления.

## Определение готового MVP

MVP готов, когда два игрока и зритель могут пройти полноценную партию, пережить переподключение, восстановить игру после перезапуска сервера и открыть сохранённую историю без ручного исправления данных.
