# Сквозной сценарий и качество

Первый сквозной сценарий проверяет всю архитектуру целиком. Он важнее полной реализации правил: если данные надёжно проходят от клиента через сервер в базу и обратно, механику можно развивать постепенно.

## Первый рабочий сценарий

1. Клиент загружает application feature flags при инициализации.
2. Пользователь входит через Google, Telegram или Yandex ID.
3. Сервер создаёт сессию War Chest.
4. Пользователь создаёт игру.
5. Сервер повторно читает runtime-файл и записывает feature flags в
   `GameCreated`.
6. Второй пользователь присоединяется из другой вкладки.
7. Клиенты получают зафиксированные для игры флаги.
8. Первый игрок запускает партию без повторного чтения runtime-файла, используя
   флаги из `GameCreated`.
9. Игроки по очереди выполняют тестовые ходы без полных игровых правил.
10. Сервер сохраняет события и рассылает обновления.
11. Игрок переходит к прошлому ходу и проигрывает отрезок партии, пока live-игра
    продолжает получать события.
12. Игрок возвращается к актуальному состоянию и отправляет команду с текущей
    версией игры.
13. Зритель без задержки видит общедоступное состояние.
14. Игрок отключается, а остальные видят время ожидания.
15. Игрок обновляет страницу и возвращается в игру до таймаута.
16. Сервер перезапускается и восстанавливает игру вместе с исходными флагами из PostgreSQL.
17. Партия завершается и появляется в профилях обоих игроков.
18. Каждый игрок может открыть свой профиль, профиль соперника и просмотр
    завершённой партии.
19. После проверки инфраструктуры тестовая механика заменяется полными правилами.

## Тестирование

### Игровой движок

- допустимые и запрещённые команды;
- очередность ходов;
- восстановление состояния из событий;
- восстановление безопасного представления из `GameViewEventData`;
- завершение игры;
- отсутствие скрытых данных в представлениях.

### Сервер

- загрузка и валидация YAML-конфигурации;
- загрузка JSON feature flags без проверки схемы;
- endpoint с application feature flags;
- запись полного snapshot флагов в `GameCreated`;
- отсутствие повторного чтения runtime-файла при старте партии;
- использование игровых флагов вместо актуального runtime-файла;
- восстановление флагов из истории;
- Google, Telegram и Yandex ID login;
- создание, проверка и отзыв сессии;
- получение публичного профиля без внешних идентичностей;
- история только завершённых игр пользователя с ролью игрока;
- сортировка и cursor-пагинация истории профиля;
- миграции на чистой базе;
- создание игры и присоединение;
- повторный `commandId`;
- связь нескольких событий с одной принятой командой;
- конфликт версий;
- команда от зрителя;
- транзакционное сохранение;
- восстановление после перезапуска;
- расчёт reconnect deadline;
- поражение после истечения reconnect deadline;
- выдача актуального состояния из `ActiveGame`;
- восстановление из полной истории после перезапуска;
- восстановление из полной истории при просмотре завершённой игры;
- replay только по цепочке событий;
- одинаковая фильтрация истории ходов в HTTP и Socket.IO;
- непрерывная нумерация безопасных событий при скрытых изменениях;
- фильтрация данных для зрителя.

### Пакет базы данных

- загрузка `env.yaml`, локального переопределения и явных переменных с нужным приоритетом;
- генерация миграции после изменения Drizzle-схемы;
- применение всех миграций к пустой PostgreSQL;
- повторный запуск миграций без изменения уже подготовленной схемы;
- ограничения уникальности и внешние ключи;
- связь игровых событий с метаданными команды;
- откат транзакции при ошибке сохранения игровых событий;
- создание тестовых данных отдельной командой.

### Пакет авторизации

- загрузка собственного `env.yaml` с локальным и явным переопределением;
- проверка ответов каждого провайдера;
- защита redirect flow через `state` и PKCE;
- Yandex callback через зарегистрированный localhost Redirect URI;
- загрузка, нормализация и сохранение аватара провайдера;
- сохранение прежнего аватара при ошибке обновления;
- создание, проверка и отзыв сессии War Chest;
- отсутствие OAuth-токенов и provider secrets в клиентской сборке.

### Клиент

- загрузка application flags при инициализации;
- получение feature flags из события и snapshot;
- неизменность базовых флагов real-игры;
- переключатель backend внутри `/login` до входа;
- dev-панель по кнопке в навигации после входа;
- persisted-переключение real/fake backend;
- единые API- и game-connection-контракты для обоих backend;
- lazy loading fake backend только в development;
- сохранение fake-данных и feature flags в IndexedDB через `idb`;
- две fake-сессии в разных вкладках одного origin;
- отдельный seeded fake-аккаунт для каждой provider-кнопки;
- fake login без OAuth popup, redirect и внешних SDK;
- Google, Telegram и Yandex ID login;
- загрузка аватара только через API War Chest;
- единый экран профиля для текущего пользователя и другого игрока;
- список завершённых игр в профиле;
- постраничная загрузка истории;
- переход из карточки истории к просмотру игры;
- группировка событий активной игры по командам;
- переход по истории ходов назад и вперёд;
- воспроизведение выбранного диапазона команд;
- ожидание завершения анимации события перед следующей командой;
- мгновенное применение команды без настроенных анимаций;
- корректное состояние после отмены анимации или ручного перехода;
- независимость `liveState` и локального `viewedState`;
- вычисление доступных действий и `expectedVersion` только из live-состояния;
- получение live-событий во время просмотра прошлого;
- получение snapshot;
- последовательное применение событий;
- reconnect;
- рассинхронизация версий;
- отображение ошибок;
- блокировка недоступных действий.

### Сквозные тесты

- два игрока в разных браузерных контекстах;
- игроки и зритель;
- вход через каждого провайдера;
- аватар Telegram-пользователя доступен клиенту без доступа к доменам Telegram;
- завершённая игра появляется в профилях обоих игроков;
- игра зрителя не появляется в его истории;
- текущий пользователь может открыть собственный профиль и профиль соперника;
- игрок просматривает прошлый ход, пока второй игрок продолжает партию;
- анимация доставки жетона завершается до воспроизведения следующей команды;
- команда без анимации не создаёт искусственной задержки;
- live-состояние обновляется во время локальной анимации истории;
- новые события не сбрасывают локальную точку просмотра истории;
- команда после просмотра истории отправляется с актуальной версией;
- возврат в live показывает все события, пришедшие во время просмотра;
- использование application flags вне игры;
- независимое получение game flags при создании игры;
- сохранение выбранного backend и fake-данных после reload;
- два fake-пользователя проходят партию в разных вкладках без сервера;
- Google и Telegram в разных вкладках создают разные fake-сессии;
- повторный fake-вход через один provider находит тот же аккаунт;
- две вкладки одного fake-аккаунта не могут занять два места в игре;
- совместная fake-игра требует двух разных provider-аккаунтов;
- fake logout одной вкладки не завершает сессию другой;
- browser-only fake-режим не требует отдельного локального сервера;
- изменение fake feature flags синхронизирует обе вкладки;
- production bundle не содержит fake backend и `@war-chest/fake-database`;
- атомарная замена runtime-файла без сборки и деплоя приложения;
- замена runtime-файла между созданием и стартом не меняет флаги игры;
- игра, созданная до замены runtime-файла, сохраняет старые флаги, а созданная
  после замены получает обновлённые;
- обновление страницы;
- временная потеря соединения;
- поражение игрока, не вернувшегося до deadline;
- синхронизация из актуального состояния `ActiveGame`;
- восстановление состояния выгруженной игры из цепочки событий;
- просмотр завершённой игры без состояния в памяти;
- перезапуск сервера во время незавершённой партии.

## Команды разработки

В корневом `package.json` должны появиться единые команды:

```text
yarn dev
yarn dev:server
yarn dev:web
yarn db:up
yarn db:down
yarn db:generate
yarn db:migrate
yarn db:seed
yarn db:studio
yarn test
yarn build
```

Локальная разработка:

```text
PostgreSQL  — Docker
Server      — локальный Node.js-процесс
Client      — локальный Vite
```

Контейнеризацию сервера и клиента добавляем после готовности первого сквозного сценария.

## Что не входит в MVP

- Redis;
- Kubernetes;
- Helm;
- микросервисная архитектура;
- брокер сообщений;
- несколько экземпляров Node.js;
- сложный event-sourcing-фреймворк.

## Определение готового MVP

Инфраструктурный MVP готов, когда два авторизованных игрока и зритель могут пройти техническую партию, пережить переподключение, восстановить игру после перезапуска сервера и открыть сохранённую историю без ручного исправления данных.

После этого реализуем полные правила и считаем игровым MVP версию, в которой тот же сценарий проходит уже с настоящей механикой War Chest.
