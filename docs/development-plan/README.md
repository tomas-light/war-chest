# План разработки веб-игры

Этот раздел описывает путь до первой рабочей версии War Chest: два игрока проходят партию, зритель наблюдает за ней, сервер сохраняет события, а завершённая игра появляется в истории участников.

План нужен как общая точка обсуждения. Здесь фиксируем порядок работ, границы MVP и решения, которые ещё предстоит принять.

## От чего мы отталкиваемся

В репозитории уже подготовлен Yarn Workspaces-монорепозиторий:

```text
apps/
  server/       Node.js-сервер
  web/          React-клиент
packages/
  game-engine/  общая игровая логика и типы
```

Для первой версии используем:

- PostgreSQL в Docker как постоянное хранилище;
- Node.js, Fastify и Socket.IO на сервере;
- React и Vite на клиенте;
- общий TypeScript-пакет `game-engine`;
- журнал игровых событий как источник истины;
- состояние активных игр в памяти одного серверного процесса.

Redis, Kubernetes, микросервисы и несколько экземпляров сервера на этом этапе не нужны.

## Основные принципы

### Сервер принимает окончательное решение

Клиент отправляет намерение сделать ход, а сервер проверяет права, очередь и правила. Только после сохранения результата сервер сообщает участникам, что ход принят.

### История событий — источник истины

Постоянно храним не единственную копию текущего состояния, а подтверждённые события игры. После перезапуска сервер может восстановить состояние, последовательно применив их.

### WebSocket — канал доставки

Socket.IO ускоряет обмен сообщениями, но не хранит игру. После подключения или рассинхронизации клиент получает актуальный снимок состояния с сервера.

### Скрытые данные остаются на сервере

Каждый игрок и зритель получает только разрешённое ему представление игры. Полное внутреннее состояние не отправляется всем участникам комнаты.

## Решения, которые предстоит обсудить

- какой минимальный набор правил войдёт в первый игровой сценарий;
- какая авторизация нужна для MVP;
- нужны ли зрителям скрытые или отложенные данные;
- как долго незавершённая игра может ждать отключившегося игрока;
- какие данные необходимы для повтора завершённой партии;
- когда добавлять снимки состояния поверх истории событий.
