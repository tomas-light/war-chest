# План разработки веб-игры

Этот раздел описывает путь до первой рабочей версии War Chest: два игрока
проходят партию, зритель наблюдает за ней, сервер сохраняет события, а
завершённая игра появляется в профилях участников.

План нужен как общая точка обсуждения. Здесь фиксируем порядок работ, границы MVP и решения, которые ещё предстоит принять.

## От чего мы отталкиваемся

В репозитории уже подготовлен Yarn Workspaces-монорепозиторий:

```text
apps/
  server/       Node.js-сервер
  web/          React-клиент
packages/
  auth/         OAuth-провайдеры и сессии War Chest
  database/     схема PostgreSQL, подключение и миграции
  fake-database/ схема IndexedDB для разработки клиента без сервера
  game-engine/  общая игровая логика и типы
```

Каркасы перечисленных пакетов уже созданы. `packages/database` реализован:
добавлены PostgreSQL-схема, клиент, конфигурация, миграции и seed-данные.
`packages/auth` и `packages/fake-database` будут наполнены на соответствующих
этапах плана. Сервер будет использовать production-пакеты как
workspace-зависимости, а fake database останется browser-only зависимостью
development-сборки клиента.

Для первой версии используем:

- PostgreSQL в Docker как постоянное хранилище;
- Node.js, Fastify и Socket.IO на сервере;
- React, Vite и Feature-Sliced Design на клиенте;
- `env.yaml` и необязательные локальные файлы `env.local.yaml` для каждой конфигурационной границы;
- отдельный runtime JSON-файл с полным набором feature flags для каждого окружения;
- Google Identity Services, Telegram OpenID Connect и Yandex ID для входа;
- отдельный TypeScript-пакет `auth` для провайдеров и сессий;
- отдельный TypeScript-пакет `database` для схемы PostgreSQL и миграций;
- отдельный browser-only пакет `fake-database` для IndexedDB на базе `idb`;
- общий TypeScript-пакет `game-engine`;
- журнал игровых событий как источник истины;
- состояние активных игр в памяти одного серверного процесса.

Redis, Kubernetes, Helm, микросервисы и несколько экземпляров сервера на этом этапе не нужны. Структура конфигурации совместима с будущим Helm chart, если проект позже перейдёт на Kubernetes.

## Основные принципы

### Сервер принимает окончательное решение

Клиент отправляет намерение сделать ход, а сервер проверяет права, очередь и правила. Только после сохранения результата сервер сообщает участникам, что ход принят.

### История событий — источник истины

Постоянно храним не единственную копию текущего состояния, а подтверждённые
события игры. Пока игра активна, её актуальное состояние находится в
`ActiveGame`. Если объекта нет в памяти после перезапуска, выгрузки или при
просмотре истории, сервер восстанавливает состояние, последовательно применяя
полную цепочку событий.

### WebSocket — канал доставки

Socket.IO ускоряет обмен сообщениями, но не хранит игру. После подключения или
рассинхронизации клиент получает актуальное безопасное представление состояния
с сервера.

### Просмотр истории не останавливает игру

На странице активной игры участник может локально перейти к прошлому ходу или
проиграть выбранный отрезок партии. При этом клиент продолжает принимать
события и поддерживать отдельное актуальное состояние. Доступные команды всегда
вычисляются из него, поэтому локальная точка просмотра не влияет на серверную
игру и других участников. События выбранного отрезка применяются
последовательно: UI может анимировать отдельный переход и только после его
завершения перейти к следующей команде.

### Скрытые данные остаются на сервере

Каждый игрок получает общую информацию поля и только свою частную информацию. Зритель в реальном времени, без искусственной задержки, видит ту же общедоступную часть поля, которую видят все игроки. Чужие карты на руках, секретные цели и другие частные данные зрителю не отправляются.

### Feature flags фиксируются при создании игры

Feature flags хранятся вне сборки и deployment-артефакта приложения. У `production`, `dev` и `localhost` есть собственный JSON-файл с полным набором флагов.

При инициализации приложения клиент загружает текущий набор с сервера для общего UI и разделов вне игры.

При создании новой игры сервер повторно читает актуальный файл и записывает
полученный snapshot в событие `GameCreated`. С этого момента флаги игры
неизменяемы: ожидание участников, старт партии, команды, reconnect и replay
используют значения из истории игры. Замена runtime-файла влияет только на игры,
которые будут созданы после неё, а общий UI увидит новые значения после
следующей инициализации приложения.

Благодаря этому уже развёрнутую функцию можно включить или выключить для новых
игр без новой сборки и цикла деплоя, не меняя поведение уже созданных игр.

### Таймаут отключённого игрока — часть конфигурации

Допустимое время отсутствия задаётся в минутах в серверном `env.yaml`. Это числовая политика работы игры, а не feature flag. В snapshot сервер передаёт клиенту вычисленный момент окончания ожидания. Если игрок не возвращается вовремя, сервер записывает ему поражение по причине `disconnectTimeout`.

### Для replay достаточно событий

Отдельные данные для повтора не храним. Завершённая партия воспроизводится по той же неизменяемой цепочке событий. Недетерминированные результаты, feature flags и версия правил должны быть зафиксированы в событиях, чтобы replay не зависел от текущей конфигурации или случайности.
