# Game service и синхронизация

`GameService` управляет прикладным сценарием, а `ActiveGames` хранит live state.
Для незавершённой игры cache содержит `GameState` и
`Map<userId, Set<socketId>>`. Несколько socket одного пользователя нужны для
параллельно открытых вкладок и повторных соединений; доменное участие игрока от
их количества не меняется.

## Очередь и загрузка

`ActiveGames.runExclusive(gameId, operation)` добавляет операцию после последней
операции той же игры. Ошибка одной операции возвращается её вызывающему коду,
но техническое продолжение очереди успешно завершается, поэтому следующие
операции не блокируются. У разных `gameId` независимые очереди.

Если cache пуст, service читает строку игры и полную проверенную историю,
восстанавливает `GameState` и сохраняет незавершённую игру в `ActiveGames`.
Завершённая игра используется только для текущей операции. Принудительная
перезагрузка после duplicate или version race заменяет state через
`ActiveGames.store`, сохраняя уже зарегистрированные runtime connections.
Exact duplicate сам по себе не удаляет незавершённую игру из cache.

## Создание игры

Service сначала вычисляет request hash и ищет `commandId` в
`processed_commands`:

- exact duplicate загружает ранее созданную игру и возвращает прежний
  `gameId`;
- несовпадающая identity возвращает `commandIdConflict`;
- только действительно новая команда читает runtime feature flags.

Поэтому повтор успешного `CreateGame` работает даже при временно недоступном
файле feature flags. Для новой команды ошибка чтения возвращает
`featureFlagsUnavailable`; успешно прочитанный snapshot попадает в
`GameCreated` и больше не перечитывается для этой игры. Repository повторно
классифицирует duplicate/conflict на случай конкурентной вставки. Если
пользователь уже занимает место в другой незавершённой партии, новая команда
создания возвращает `playerAlreadyInGame`. Иначе новая игра
сохраняется только с `GameCreated`, где `creatorId` фиксирует владельца права
запуска, и пустыми составами. Создатель не получает место автоматически и
выбирает его позднее через обычный `JoinGame`.

Одновременно service ставит таймер от database-значения `games.createdAt`.
Первый сохранённый `PlayerJoined` снимает его: таймаут относится только к игре,
где никто так и не занял место, а не ко всей подготовке партии.

## Таймаут пустой waiting-игры

После `EMPTY_WAITING_GAME_TIMEOUT_MINUTES` service входит в ту же
`ActiveGames.runExclusive`-очередь, что и пользовательские команды, и просит
repository удалить игру. Repository повторяет проверку под database lock, так
что срабатывание таймера одновременно с `JoinGame` не может удалить уже занятую
игру. После успешного удаления cache очищается, подписчики лобби получают
обновление, а подключённые к комнате игры клиенты — `game_not_found`.

Временная ошибка хранения не оставляет игру навсегда: удаление повторяется с
exponential backoff от 1 до 60 секунд. При штатном `GameService.close()` эти
таймеры очищаются вместе с reconnect timers.

## Выполнение команды

Команда проходит следующую цепочку внутри очереди игры:

1. service вычисляет request hash и ищет сохранённый `commandId`;
2. exact duplicate перезагружает актуальную историю и возвращает безопасную
   синхронизацию, conflict завершается без проверки версии;
3. service загружает игру и сравнивает `expectedVersion` с
   `state.lastEventSequence`;
4. для `StartGame` и `SwapPlayerPositions` проверяется совпадение пользователя с `state.creatorId`, а
   для остальных команд кроме `JoinGame` — persisted-участие игрока;
5. для `JoinGame` определяется первое присоединение, повтор текущей позиции или
   перенос существующего участника, проверяются занятость цели и отсутствие
   другой текущей игры;
6. `game-engine.decide` формирует события;
7. пустой результат становится `commandRejected` без строки
   `processed_commands` и без изменения версии;
8. service строит изменения SQL-проекций и передаёт всё repository;
9. после commit события последовательно применяются к live state;
10. подписчики получают диапазон обновления от предыдущей версии.

`JoinGame` доступен и зрителю, и существующему участнику ожидающей игры. Зритель
занимает свободную позицию через `PlayerJoined`. Пока остаётся вторая свободная
позиция, участник может перейти на неё через `PlayerPositionChanged`; repository
обновляет существующую строку `game_participants`. Если пользователь уже
занимает ту же комбинацию `team + seat`, service возвращает `alreadyJoined` и
текущий view, а место другого игрока — `gamePositionOccupied`. Все остальные
игровые команды доступны только persisted-игрокам; зрители получают
`gameCommandForbidden`.

`StartGame` — отдельное исключение из проверки persisted-участия. Заполненную
игру может запустить только пользователь из `GameCreated.creatorId`, даже если
он не занимал место. Присоединившийся игрок без этого права получает
`gameCommandForbidden`; движок повторяет ту же проверку перед созданием
`GameStarted`.

`SwapPlayerPositions` доступен тому же создателю только в ожидающей игре с
двумя игроками. Движок создаёт один `PlayerPositionsSwapped`, а repository
атомарно обновляет обе SQL-проекции.

## Безопасные views и уведомления

Service определяет viewer по `game_participants` и текущему состоянию. Игрок
получает общую и собственную приватную информацию, зритель — только публичную.
Безопасный `GameView` содержит `creatorId`, чтобы клиент мог показать действие
запуска правильному пользователю. Сырые `GameState` и `GameEventData`
transport-слою не возвращаются.

Для лобби service читает незавершённые игры с участниками, преобразует их в
публичные профили и добавляет `currentPlayerGameId` текущего пользователя.
Открытие игры само по себе всегда подключает постороннего
пользователя как runtime-зрителя; отдельная строка участника для него не
создаётся. В ожидающей игре со свободной позицией пользователь может отдельно
выполнить `JoinGame`. При заполненных составах и после старта ему остаётся
только наблюдение.

Для синхронизации service отдаёт безопасный event tail после известного
`afterSequence`. Если клиент прислал sequence новее текущей версии, вместо
некорректного хвоста возвращается полный snapshot. История дополнительно
проверяется на пропуски и совпадение последнего sequence с текущей версией.

Создание игры, команда игрока, system presence и удаление просроченной пустой
игры вызывают одно уведомление `GameService`. `createSocketServer` оформляет
одну подписку: отправляет сигнал `lobby:updated` общей комнате лобби и строит
персональную синхронизацию для каждого socket комнаты конкретной игры. Adapter
команды сам не дублирует broadcast. Если отправитель команды ещё не вошёл в
игровую комнату, он получает безопасные события непосредственно из результата
команды; участник комнаты получает их через общую подписку. Ошибка отдельного
listener не отменяет уже сохранённую команду и не мешает остальным listeners.

Transport-форматы и обработка результатов описаны в
[Socket.IO](../socket-io.md) и [HTTP API](../http-api.md).
