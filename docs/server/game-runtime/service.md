# Game service и синхронизация

`GameService` управляет прикладным сценарием, а `ActiveGames` хранит live state.
Для незавершённой игры cache содержит `GameState` и
`Map<userId, Set<socketId>>`. Несколько socket одного пользователя нужны для
параллельно открытых вкладок и повторных соединений; доменное участие игрока от
их количества не меняется.

## Очередь и загрузка

`ActiveGames.runExclusive(gameId, operation)` добавляет операцию после последней
операции той же игры. Ошибка одной операции возвращается её вызывающему коду,
но техническое продолжение очереди успешно завершается, поэтому следующие
операции не блокируются. У разных `gameId` независимые очереди.

Если cache пуст, service читает строку игры и полную проверенную историю,
восстанавливает `GameState` и сохраняет незавершённую игру в `ActiveGames`.
Завершённая игра используется только для текущей операции. Принудительная
перезагрузка после duplicate или version race заменяет state через
`ActiveGames.store`, сохраняя уже зарегистрированные runtime connections.
Exact duplicate сам по себе не удаляет незавершённую игру из cache.

## Создание игры

Service сначала вычисляет request hash и ищет `commandId` в
`processed_commands`:

- exact duplicate загружает ранее созданную игру и возвращает прежний
  `gameId`;
- несовпадающая identity возвращает `commandIdConflict`;
- только действительно новая команда читает runtime feature flags.

Поэтому повтор успешного `CreateGame` работает даже при временно недоступном
файле feature flags. Для новой команды ошибка чтения возвращает
`featureFlagsUnavailable`; успешно прочитанный snapshot попадает в
`GameCreated` и больше не перечитывается для этой игры. Repository повторно
классифицирует duplicate/conflict на случай конкурентной вставки.

## Выполнение команды

Команда проходит следующую цепочку внутри очереди игры:

1. service вычисляет request hash и ищет сохранённый `commandId`;
2. exact duplicate перезагружает актуальную историю и возвращает безопасную
   синхронизацию, conflict завершается без проверки версии;
3. service загружает игру и сравнивает `expectedVersion` с
   `state.lastEventSequence`;
4. для любой команды кроме `JoinGame` проверяется persisted-участие игрока;
5. для `JoinGame` отдельно проверяются повторное участие и занятость позиции;
6. `game-engine.decide` формирует события;
7. пустой результат становится `commandRejected` без строки
   `processed_commands` и без изменения версии;
8. service строит изменения SQL-проекций и передаёт всё repository;
9. после commit события последовательно применяются к live state;
10. подписчики получают диапазон обновления от предыдущей версии.

`JoinGame` доступен пользователю, который ещё не является участником, иначе он
не смог бы занять место. Если пользователь уже занимает ту же комбинацию
`team + seat`, service возвращает `alreadyJoined` и текущий view. Попытка
сменить своё место отклоняется как `commandRejected`, а место другого игрока —
как `gamePositionOccupied`. Все остальные игровые команды доступны только
persisted-игрокам; зрители получают `gameCommandForbidden`.

## Безопасные views и уведомления

Service определяет viewer по `game_participants` и текущему состоянию. Игрок
получает общую и собственную приватную информацию, зритель — только публичную.
Сырые `GameState` и `GameEventData` transport-слою не возвращаются.

Для синхронизации service отдаёт безопасный event tail после известного
`afterSequence`. Если клиент прислал sequence новее текущей версии, вместо
некорректного хвоста возвращается полный snapshot. История дополнительно
проверяется на пропуски и совпадение последнего sequence с текущей версией.

Каждое успешно сохранённое изменение — команда игрока или system presence —
вызывает одно уведомление `GameService`. `createSocketServer` оформляет одну
подписку и строит персональную синхронизацию для каждого socket комнаты.
Adapter команды сам не дублирует broadcast. Если отправитель команды ещё не
вошёл в комнату, он получает безопасные события непосредственно из результата
команды; участник комнаты получает их через общую подписку. Ошибка отдельного
listener не отменяет уже сохранённую команду и не мешает остальным listeners.

Transport-форматы и обработка результатов описаны в
[Socket.IO](../socket-io.md) и [HTTP API](../http-api.md).
