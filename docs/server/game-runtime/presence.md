# Соединения, reconnect и recovery

Socket.IO connection — runtime-сущность, а участие игрока — persisted-сущность.
`game:join` регистрирует socket в `ActiveGames` и входит в комнату, но не создаёт
`game_participants`: место занимает только доменная команда `JoinGame`.

## Подключение и отключение

Один пользователь может держать несколько socket одной игры, например в двух
вкладках. Повторная регистрация того же socket идемпотентна. Физический
disconnect или `game:leave` удаляет только конкретный socket; пользователь
считается отключённым после удаления последнего.

Отключение зрителя и игрока в незапущенной игре не меняет историю. Для активного
игрока последний socket создаёт `PlayerDisconnected` с точным ISO
`reconnectDeadline`, вычисленным из `DISCONNECTED_PLAYER_TIMEOUT_MINUTES`.
Подключение до срока создаёт `PlayerReconnected`. Оба события сохраняются до
изменения live state и рассылаются как обычные безопасные events.

## Истечение deadline

Первый timer ждёт до сохранённого deadline. После срабатывания service входит в
общую последовательную очередь игры и повторно проверяет, что:

- игра всё ещё активна;
- игрок всё ещё отключён;
- в состоянии остался именно обрабатываемый deadline.

Только после этого game engine формирует `PlayerDefeated` с причиной
`disconnectTimeout` и при выполнении условия завершения — `GameFinished`.
Системные события и проекции сохраняются одной транзакцией, затем применяются к
state и рассылаются.

Временная ошибка repository не отменяет поражение. Service повторяет обработку
с exponential backoff: 1, 2, 4 секунды и далее, не больше 60 секунд между
попытками. Если engine временно вернул пустой набор событий при всё ещё
актуальном deadline, используется тот же retry. Перед каждой попыткой условия
проверяются заново, поэтому reconnect, завершение игры или замена deadline
безопасно останавливают старый timer.

## Восстановление и остановка

При старте `recoverGames()` параллельно восстанавливает активные партии и
cleanup пустых ожидающих игр. Для активных игр service replay-ит полную историю
и восстанавливает timers отключённых игроков. Будущий reconnect deadline
планируется на оставшееся время, истёкший обрабатывается сразу. Для пустой
`waiting`-игры будущий срок удаления планируется от `games.createdAt`, а уже
истёкший обрабатывается до начала прослушивания HTTP-порта. Блокировка строки и
повторная проверка состояния защищают оба сценария от конкурентной обработки.

При штатном закрытии `GameService.close()` помечает service закрытым, очищает
reconnect и cleanup timers, а также listeners. Уже начатая либо ошибочная
фоновая операция после этого не может запланировать новый retry. Порядок
остановки всего приложения описан в [запуске server](../hosting.md).
