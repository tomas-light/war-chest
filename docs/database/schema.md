# Схема данных

Схема разделена на авторизационные и игровые таблицы. Она хранит факты и
метаданные, необходимые серверу, но не содержит реализацию OAuth-провайдеров
или правил War Chest.

## Пользователи и авторизация

| Таблица           | Что хранит                                                              |
| ----------------- | ----------------------------------------------------------------------- |
| `users`           | Внутреннего пользователя, отображаемое имя и время создания             |
| `user_avatars`    | Нормализованное изображение `bytea`, MIME type, hash и время обновления |
| `email_login_challenges` | Одноразовые коды входа и их срок действия                       |
| `email_login_failures` | Неудачные проверки для ограничения перебора                        |
| `email_registration_tickets` | Одноразовое завершение первого входа                       |
| `auth_sessions`   | Hash session token, срок действия и время отзыва                        |

У одного пользователя может быть не больше одного аватара. Пара `provider` и
`provider_subject` уникальна, поэтому повторный вход находит ту же внешнюю
идентичность. Hash сессии также уникален и проиндексирован для быстрого поиска;
исходный token в PostgreSQL не сохраняется.

Удаление пользователя каскадно удаляет его аватар, внешние идентичности и
сессии.

## Игры и история событий

| Таблица               | Что хранит                                                                                    |
| --------------------- | --------------------------------------------------------------------------------------------- |
| `games`               | Статус, победившую команду, текущую версию и время создания, старта и завершения              |
| `game_participants`   | Игрока и выбранную позицию: команду вместе с местом                                           |
| `active_game_players` | Единственную незавершённую игру, в которой пользователь занимает место                        |
| `processed_commands`  | Принятый `commandId`, пользователя, тип, SHA-256 hash канонического запроса и время обработки |
| `game_events`         | Упорядоченное типизированное событие, JSON payload и команду-причину                          |

`games.currentVersion` всегда равен `sequence` последнего сохранённого события
этой игры. Пустая созданная игра содержит только `GameCreated` с
`sequence = 1`, `creatorId` и имеет версию 1. Идентификатор создателя хранится в
истории, а не в `game_participants`, поэтому право запуска не зависит от занятия
места. `PlayerJoined` появляется позднее, когда любой пользователь, в том числе
создатель, отдельно выбирает свободную позицию. Нулевая версия допустима только
внутри транзакции до сохранения первого события.

Миграция `0003_reset_game_creator` удаляет только старые игры, события,
участников и обработанные игровые команды перед переходом на обязательный
`creatorId`. Пользователи, identities и auth sessions сохраняются.

`game_events` — постоянный источник игрового состояния. Полные снимки
`GameState` в базе не хранятся: сервер восстанавливает состояние, применяя
события по `sequence`.

`processed_commands` защищает от повторного применения команды после reconnect.
Exact duplicate определяется по игре, пользователю, типу и `request_hash`; при
создании игры сгенерированный server-side `gameId` в сравнение не входит.
`request_hash` — lowercase SHA-256 и не раскрывает исходный payload. События с
одним `command_id` можно объединить в одно действие в истории ходов. Системное
событие без команды хранит `NULL`.

Игрок выбирает команду и место одновременно при присоединении. Составы команд
восстанавливаются из `PlayerJoined`, `PlayerPositionChanged` и `PlayerLeft`, а
`game_participants.team` и `game_participants.seat` служат актуальной проекцией
выбранной позиции для прикладных запросов. Победившая команда остаётся фактом
`GameFinished` и дублируется в `games.winner_team`, чтобы история профиля не
восстанавливала каждую завершённую игру из событий. Зритель в
`game_participants` не записывается.

`active_game_players.user_id` — первичный ключ. Строка добавляется атомарно с
первым `PlayerJoined` и удаляется при `GameFinished`. Поэтому PostgreSQL не
позволяет одному пользователю одновременно занять места в разных ожидающих или
активных играх. `PlayerLeft` до старта удаляет обе проекции, а исторические
строки `game_participants` после завершения сохраняются.
`PlayerPositionsSwapped` обновляет обе позиции одной транзакцией.

Миграция `0004_single_active_game` добавляет эту проекцию. Предыдущая миграция
уже очистила только игровые таблицы, поэтому данные авторизации остаются
нетронутыми.

## Ограничения целостности

Схема не полагается только на проверки прикладного кода:

- версия игры не может быть отрицательной;
- пара игры и пользователя в `game_participants` является первичным ключом;
- пользователь является первичным ключом в `active_game_players`;
- место игрока положительно;
- команда и место игрока обязательны;
- сочетание команды и места уникально внутри игры;
- идентификатор обработанной команды уникален;
- request hash обработанной команды содержит 64 lowercase hex-символа;
- `sequence` события уникален внутри игры и всегда положителен;
- версия формата события всегда положительна;
- событие с `command_id` ссылается на существующую обработанную команду;
- внешние ключи защищают связи пользователей, игр, участников и событий.

Индексы покрывают поиск сессии, идентичностей пользователя, истории игр,
обработанных команд и последовательности событий. Drizzle relations позволяют
выполнять типизированные связанные запросы через публичный client.
