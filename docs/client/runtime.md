# Runtime-поведение клиента

Этот документ описывает только текущее поведение `apps/web`. Целевые игровые
сценарии находятся в development plan и не считаются реализованными, пока их
нет в коде.

## Запуск приложения и провайдеры

`src/main.tsx` монтирует `App` в элемент `#root` и включает React `StrictMode`.
Если корневого элемента нет, запуск останавливается с явной ошибкой.

На уровне приложения подключены два provider:

- `QueryClientProvider`: запросы повторяются один раз, а `staleTime` равен
  30 секундам;
- `BrowserRouter`: клиент использует обычные browser history URL без hash.

Через TanStack Query загружается текущая auth session. `401` означает
анонимного пользователя; сетевой сбой или некорректный ответ показывает экран
повторной проверки.

## Маршруты

URL создаются через `nice-web-routes`, а React Router использует их в
Declarative Mode.

| URL                   | Текущий экран                                     |
| --------------------- | ------------------------------------------------- |
| `/`                   | redirect на `/lobby`                              |
| `/login`              | вход через Google, Telegram или Yandex ID         |
| `/lobby`              | ожидающие и активные игры                         |
| `/games/new`          | создание пустой игры                              |
| `/games/:gameId`      | подготовка составов, запуск или режим зрителя     |
| `/games/play/:gameId` | игровое поле, участники, действия и история ходов |
| `/profile`            | заглушка профиля текущего пользователя            |
| `/users/:userId`      | та же заглушка профиля с параметром пользователя  |
| `/history/:gameId`    | заглушка просмотра завершённой игры               |
| любой другой URL      | redirect на `/lobby`                              |

Все маршруты, кроме `/login`, требуют действующую сессию. До окончания проверки
показывается экран загрузки. Анонимный пользователь переходит на `/login`, а
после входа возвращается к исходному URL. Авторизованный пользователь при
переходе на `/login` возвращается в лобби.

## Авторизация

В real-режиме клиент получает сессию через `GET /api/auth/session`. На экране
входа отображаются Google, Telegram и Yandex ID: реализованные провайдеры не
управляются runtime feature flags и не зависят от загрузки application flags.

Для Google дополнительно нужен непустой `GOOGLE_CLIENT_ID`. Официальная кнопка
Google Identity Services возвращает ID token, который отправляется в
`POST /api/auth/google`. Telegram и Yandex переводят браузер на соответствующий
`/api/auth/<provider>/start`. Токены внешних провайдеров клиент не сохраняет.

После входа верхняя навигация показывает аватар, имя пользователя и кнопку
выхода. Если сохранённого изображения нет, компонент аватара показывает
инициалы.
Logout вызывает `POST /api/auth/logout`, очищает query сессии и возвращает
пользователя на `/login` через общий auth guard.

В development fake-режим не загружает Google SDK и не выполняет внешние
redirect. Каждая provider-кнопка выбирает отдельного пользователя со стабильным
UUID из seed `@war-chest/fake-database`. Identity и пользователь читаются из
IndexedDB, новая auth session записывается через `fakeDatabase.sessions`, а
logout отзывает эту запись.

В `sessionStorage` хранится только ID выбранной сессии, чтобы разные вкладки
одного origin могли оставаться разными fake-пользователями. После reload клиент
передаёт этот ID общему `SharedWorker`. Worker проверяет активную сессию в
IndexedDB, связывает пользователя с `MessagePort` вкладки и возвращает публичный
профиль. Login, session restore и logout выполняются через тот же RPC; вкладка
не открывает fake database напрямую.

Активная вкладка дополнительно удерживает эксклюзивный Web Lock своей fake
session. Браузер копирует `sessionStorage` при дублировании вкладки, но дубликат
не может получить уже занятый lock, удаляет скопированный ID и открывает экран
входа. Logout отзывает session только при наличии lock текущей вкладки, поэтому
дубликат не может завершить session исходной вкладки.

## Выбор backend

Переключатель backend загружается динамически только при `import.meta.env.DEV`.
До входа он находится внутри `/login`, поэтому перейти на fake backend можно
даже при недоступном real API. После входа переключатель находится в
dev-панели, которая открывается кнопкой `Dev` в верхней навигации. Выбранное
значение `real` или `fake` сохраняется через Zustand `persist` под ключом
`war-chest-dev-backend`, после чего страница полностью перезагружается. Reload
гарантирует, что providers и соединения не смешают состояния разных backend.

В production-сборку переключатель, dev-панель, storage key и fake connection не
попадают. Там всегда используется real backend.

Fake adapter использует общий `@war-chest/fake-database` в IndexedDB и повторяет
создание пустой игры, список игр, чтение snapshot, `JoinGame` для занятия или
смены позиции, `LeaveGame`, `SwapPlayerPositions`, `StartGame` и
`SurrenderGame`. События формируются и применяются через
`@war-chest/game-engine`, зритель получает публичный view. Закрытие лобби
создателем удаляет его aggregate из IndexedDB.

В fake-режиме один `SharedWorker` обслуживает все вкладки точного origin. Каждая
вкладка использует собственный `MessagePort`, а worker владеет одним lazy
экземпляром fake database. Все RPC-запросы проходят через общую promise-очередь,
поэтому чтение состояния, решение game engine и сохранение результата одной
команды не пересекаются с командой из другой вкладки. Ошибка операции не
останавливает обработку следующих запросов.

Подписки лобби и игры получают отдельный `subscriptionId`. После сохранённого
изменения worker отправляет каждой lobby-подписке `gameId`, а подписанным на игру
вкладкам — безопасный snapshot для пользователя, связанного с их портом.
`BroadcastChannel` для fake backend больше не используется.

## Игровое соединение

Real connection создаёт `socket.io-client` с `autoConnect: false` и путём
`/api/socket.io`. Публичный интерфейс позволяет:

- открыть и закрыть соединение;
- отправить `game:join` и `game:leave`;
- запросить `game:sync` после известного sequence number.

Fake connection реализует тот же публичный интерфейс через RPC к
`SharedWorker`. `join` регистрирует игровую подписку и возвращает полный
snapshot, а последующие изменения приходят адресно по `subscriptionId`.
Текущая fake-синхронизация также возвращает полный snapshot независимо от
`afterSequence`.

Лобби использует отдельное соединение. После подключения оно отправляет
`lobby:subscribe`, а входящий `lobby:updated` инвалидирует TanStack Query списка
игр. Полный список и публичные профили по-прежнему загружаются через HTTP, так
что WebSocket-сообщение служит сигналом обновления, а не второй копией lobby
state. Подтверждение подписки тоже запускает повторную проверку списка, чтобы
не пропустить изменение между первым HTTP-запросом и входом в Socket.IO-комнату.

Входящие `game:snapshot`, `game:events` и `game:error` проверяются Zod-схемами
из `@war-chest/api-contracts` до передачи в приложение. Ошибка схемы сейчас
выбрасывается обработчиком Socket.IO; отдельного UI для неё нет.

Страницы подготовки и активной партии находятся под одним runtime provider.
Он сначала загружает безопасный snapshot через HTTP, затем создаёт общий
Zustand vanilla store и одно игровое соединение. Переход с подготовки на
`/games/play/:gameId` меняет экран, но не закрывает socket и поэтому не создаёт
ложную пару `PlayerDisconnected` / `PlayerReconnected`.

Каждый принятый `game:snapshot` и результат применения `game:events`
сохраняются не только в Zustand store, но и в TanStack Query cache этой игры.
Новый экран не может восстановить устаревший статус `waiting` из предыдущего
HTTP-снимка и отправить игрока обратно на подготовку.

На карточке лобби у ожидающей и активной игры есть только компактная кнопка
открытия. Посторонний пользователь выбирает «Смотреть» или «Занять место» уже
на странице ожидающей игры; при заполненных составах доступно только
«Смотреть». Активная игра сразу открывается ему в режиме зрителя без выбора.
Ответ лобби содержит `currentPlayerGameId`. Если пользователь уже занял место в
незавершённой партии, действие «Новая игра» заменяется на «Вернуться в игру».
В других партиях он остаётся зрителем и не получает выбор места, пока его
текущая игра не завершится.

Создатель не занимает место автоматически. Участник ожидающей игры может
перейти на вторую свободную позицию. После заполнения обоих мест кнопка запуска
появляется только у создателя; он может запустить игру, даже если сам остался
зрителем. Рядом с `VS` создателю доступна кнопка обмена занятых позиций.
На том же экране создатель может закрыть всё лобби, а присоединившийся
не-создатель — покинуть его и освободить только своё место. В активной партии
оба игрока видят действие «Сдаться» независимо от того, чей сейчас ход; после
него экран получает завершённое состояние с победой оппонента.
Карточки лобби и оба игровых экрана показывают публичные имена и аватары
участников. Остальные участники видят ожидание запуска. Новые события:

1. игнорируются, если их sequence уже применён;
2. применяются через `applyViewEvent`, если sequence следующий;
3. переводят store в `desynchronized`, если обнаружен пропуск.

При рассинхронизации страница автоматически вызывает `game:sync` после
последнего применённого sequence. После `GameStarted` обе роли переходят на
`/games/play/:gameId`. Там уже выделены центральная область поля, оппонент над
полем, текущий игрок под ним и правая колонка действий и истории; само поле и
содержимое этих панелей пока остаются заглушками.

## Build-time конфигурация

Vite читает `apps/web/env.yaml`, затем необязательный `env.local.yaml` и явные
переменные окружения. Результат валидируется Zod. Публичная часть встраивается
в bundle как `__WEB_CONFIG__`, а настройки development-сервера остаются в
Vite.

Конфигурация принимает два ключа:

```yaml
GOOGLE_CLIENT_ID: ''
__VITE_ADDITIONAL_SERVER_ALLOWED_HOSTS: ''
```

В `__WEB_CONFIG__` попадает только `GOOGLE_CLIENT_ID`.
`__VITE_ADDITIONAL_SERVER_ALLOWED_HOSTS` разрешает точный hostname
HTTPS-туннеля в `server.allowedHosts` и не передаётся браузерному приложению.

Адрес API не конфигурируется: клиент всегда использует относительные `/api/*`
и `/api/socket.io`.
