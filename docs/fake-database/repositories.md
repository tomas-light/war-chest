# Репозитории, fixtures и проверки

Репозитории добавляют поверх таблиц операции, которые выражают реальные
контракты fake backend. Они сохраняют связанные данные атомарно и проверяют
ограничения, которые намеренно не вынесены в отдельные IndexedDB-индексы.

## Доменные операции

| Фасад          | Основные операции                                                                                          |
| -------------- | ---------------------------------------------------------------------------------------------------------- |
| `users`        | поиск по provider identity, чтение пользователя и identities, атомарное сохранение пользователя с identity |
| `sessions`     | сохранение, чтение, проверка срока действия и отзыва, отзыв активной сессии                                |
| `games`        | игры и участники, события после sequence, обработанные команды, атомарное сохранение изменений             |
| `featureFlags` | чтение и замена application runtime feature flags                                                          |

Пользовательская identity проверяется на уникальность пары
`provider + providerSubject`. Сессия может ссылаться только на существующего
пользователя, а `findActive()` не возвращает истёкшую или отозванную запись.

`games.saveChanges()` одной транзакцией сохраняет игру, изменившихся
участников, обработанную команду и новые события. Перед записью репозиторий
проверяет принадлежность данных одной игре, ссылки команды на события,
обязательные `team` и `seat` и уникальность занятых позиций. Повторный
идентификатор команды или события приводит к откату всех изменений. Повторное
сохранение участника обновляет его позицию, что позволяет fake backend
проецировать `PlayerPositionChanged` так же, как PostgreSQL repository.
При первом участии repository дополнительно проверяет все незавершённые игры
пользователя. Поэтому параллельное место в другой партии отклоняется, тогда как
просмотр не создаёт записи участника. Два участника из
`PlayerPositionsSwapped` валидируются и сохраняются как одно конечное состояние
той же IndexedDB-транзакции.

События читаются через составной индекс в порядке `sequence`, с параметрами
`afterSequence` и `limit`. `replaceFeatureFlags()` изменяет только snapshot
`featureFlags` в первом событии `GameCreated`; настройки партии и остальная
цепочка истории сохраняются.

## Начальные данные и reset

При каждом `createFakeDatabase()` выполняется идемпотентный seed. Он добавляет
только отсутствующие записи и не перезаписывает изменённые runtime flags или
профили при повторном открытии базы.

| Email                 | Имя пользователя |
| --------------------- | ----------------- |
| `archer@example.com`  | `Archer`          |
| `cavalry@example.com` | `Cavalry`         |
| `priest@example.com`  | `Warrior Priest`  |

UUID пользователей и дата создания стабильны. Благодаря этому повторный
fake-вход после reload или reset находит тот же логический аккаунт.

Начальные application feature flags:

| Flag                 | Значение |
| -------------------- | -------- |
| `gameHistory`        | `true`   |
| `nightfallExpansion` | `false`  |
| `nobilityExpansion`  | `false`  |
| `optimisticMoves`    | `false`  |
| `siegeExpansion`     | `false`  |
| `spectatorMode`      | `true`   |

Версия IndexedDB schema равна `7`. При обновлении со старой версии игровые
stores очищаются, потому что события без обязательного snapshot настроек не
переинтерпретируются новым контрактом. Fake IndexedDB считается одноразовым
development-окружением: пользователи, сессии и runtime feature flags также
очищаются, после чего seed создаёт чистые стандартные данные.

`reset()` атомарно очищает все семь stores и в той же транзакции возвращает три
seed-аккаунта и исходные feature flags. Игры, события, команды и сессии после
reset отсутствуют.

## Проверки пакета

Тесты запускаются без браузера на `fake-indexeddb`:

```shell
yarn workspace @war-chest/fake-database test
```

Набор тестов проверяет миграции и индекс, все CRUD-операции таблицы, публичный
откат транзакции, seed, ограничения репозиториев, активность сессий,
постраничное чтение событий, изменение `GameCreated` и полный reset. Типы
пакета отдельно проверяются командой:

```shell
yarn workspace @war-chest/fake-database types:build
```
