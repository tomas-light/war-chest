# Репозитории, fixtures и проверки

Репозитории добавляют поверх таблиц операции, которые выражают реальные
контракты fake backend. Они сохраняют связанные данные атомарно и проверяют
ограничения, которые намеренно не вынесены в отдельные IndexedDB-индексы.

## Доменные операции

| Фасад          | Основные операции                                                                                         |
| -------------- | --------------------------------------------------------------------------------------------------------- |
| `users`        | поиск по provider identity, чтение пользователя и identities, атомарное сохранение пользователя с identity |
| `sessions`     | сохранение, чтение, проверка срока действия и отзыва, отзыв активной сессии                               |
| `games`        | игры и участники, события после sequence, обработанные команды, атомарное сохранение изменений            |
| `featureFlags` | чтение и замена application runtime feature flags                                                        |

Пользовательская identity проверяется на уникальность пары
`provider + providerSubject`. Сессия может ссылаться только на существующего
пользователя, а `findActive()` не возвращает истёкшую или отозванную запись.

`games.saveChanges()` одной транзакцией сохраняет игру, изменившихся
участников, обработанную команду и новые события. Перед записью репозиторий
проверяет принадлежность данных одной игре, ссылки команды на события, роли,
совместное заполнение `team` и `seat` и уникальность занятых позиций. Повторный
идентификатор команды или события приводит к откату всех изменений.

События читаются через составной индекс в порядке `sequence`, с параметрами
`afterSequence` и `limit`. `replaceFeatureFlags()` изменяет только snapshot
`featureFlags` в первом событии `GameCreated`; остальные поля события и цепочка
истории сохраняются.

## Начальные данные и reset

При каждом `createFakeDatabase()` выполняется идемпотентный seed. Он добавляет
только отсутствующие записи и не перезаписывает изменённые runtime flags или
профили при повторном открытии базы.

| Provider   | Имя пользователя | Provider subject       |
| ---------- | ----------------- | ---------------------- |
| Google     | `G User`          | `fake-google-user`     |
| Telegram   | `T User`          | `fake-telegram-user`   |
| Yandex     | `Y User`          | `fake-yandex-user`     |

UUID пользователей и identities, provider subjects и дата создания стабильны.
Благодаря этому повторный fake-вход после reload или reset находит тот же
логический аккаунт.

Начальные application feature flags:

| Flag              | Значение |
| ----------------- | -------- |
| `gameHistory`     | `true`   |
| `optimisticMoves` | `false`  |
| `spectatorMode`   | `true`   |

`reset()` атомарно очищает все восемь stores и в той же транзакции возвращает
три аккаунта, identities и исходные feature flags. Игры, события, команды и
сессии после reset отсутствуют.

## Проверки пакета

Тесты запускаются без браузера на `fake-indexeddb`:

```shell
yarn workspace @war-chest/fake-database test
```

Набор из 21 теста проверяет миграцию и индекс, все CRUD-операции таблицы,
публичный откат транзакции, seed, ограничения репозиториев, активность сессий,
постраничное чтение событий, изменение `GameCreated` и полный reset. Типы
пакета отдельно проверяются командой:

```shell
yarn workspace @war-chest/fake-database types:build
```
