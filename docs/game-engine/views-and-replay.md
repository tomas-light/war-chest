# Представления и приватность

Внутренние `GameState`, `GameEventData` и runtime-объекты `ApplicableEvent` не
должны покидать сервер. Для snapshot, live-обновлений и replay пакет строит
`GameView` и сериализуемые `GameViewEventData`, уже отфильтрованные для
конкретного получателя.

## Получатели

Тип `Viewer` поддерживает две роли:

```ts
type Viewer =
  | { playerId: string; role: 'player' }
  | { role: 'spectator' };
```

В полном представлении все получатели видят статус, `lastEventSequence`, feature
flags, версию правил, игроков, очередь и публичные счётчики тестовых ходов.
Игрок дополнительно получает только собственную историю `privateMoves`. Зритель
и `playerId`, которого нет среди участников, получают пустую приватную историю.

## События для получателя

`createViewEventFor` гидратирует внутреннее событие и вызывает
`event.toViewData(viewer)`. Метод сохраняет исходные `sequence` и `version`,
поэтому цепочка клиента остаётся синхронной с внутренней историей.

Все события технического сценария имеют публичную часть. У
`TestMovePerformed` идентификатор игрока, номер хода и следующий игрок доступны
всем, а `privateData` добавляется только в событие автора хода. Второй игрок и
зритель не получают это поле вовсе.

Тип `ViewSequenceAdvanced` уже входит в публичный контракт. Он предназначен для
будущего внутреннего события, у которого нет ни одного видимого поля: такое
событие обновит `lastEventSequence` представления, но не раскроет тип или данные
скрытого факта. Текущий `createViewEventFor` его пока не создаёт, потому что
полностью скрытых событий в техническом сценарии нет.

## Snapshot и replay

Для полной синхронизации сервер вызывает `createViewFor(state, viewer)`. Для
последующих live-изменений он преобразует каждое сохранённое внутреннее событие
через `createViewEventFor` и отправляет результат нужному получателю.

Клиент применяет обновления через `applyViewEvent`. Фасад вызывает
`hydrateViewEvent(data).apply(view)`: JSON временно превращается в
`ApplicableViewEvent`, а логика применения остаётся в классе конкретного
безопасного события. Для replay клиент передаёт безопасную историю в
`restoreView`; `decide` и внутренние события при этом не нужны. Результат
восстановления из view-событий совпадает с `createViewFor` для того же итогового
состояния и получателя.

View-события используют отдельные групповые гидраторы:

- `hydrateLifecycleViewEvent` — создание, присоединение, старт и завершение;
- `hydrateTestScenarioViewEvent` — безопасная часть тестового хода;
- `hydrateSynchronizationViewEvent` — нейтральное продвижение sequence.

Эти runtime-классы получают только `GameViewEventData`. Они не имеют доступа к
полному внутреннему payload и потому не могут случайно раскрыть скрытые данные.

Пустая безопасная история означает отсутствие игры, поэтому `restoreView([])`
возвращает `null`. В непустой цепочке первым должен идти безопасный
`GameCreated`: `applyViewEvent(null, event)` создаёт представление со статусом
`waiting`. Событие другого типа до создания или повторный `GameCreated`
считаются повреждённой историей.

Движок применяет события синхронно и не управляет анимациями. Клиент может
показать переход между состояниями с любой скоростью, но состояние после
события всегда вычисляется одной и той же функцией.
