# Авторизация

`@war-chest/auth` — серверный пакет, который проверяет вход через Google,
Telegram и Yandex ID, связывает внешнюю идентичность с пользователем War Chest,
обновляет его аватар и создаёт собственную сессию. После входа игровому серверу
не нужно обращаться к OAuth-провайдеру при каждом запросе.

Пакет зависит от `@war-chest/database`, но не содержит HTTP-маршрутов,
Fastify-плагинов и кода установки cookie в ответ. Серверный адаптер должен
вызвать публичный API, перенести возвращённые параметры cookie в HTTP-ответ и
выполнить redirect там, где он нужен.

## Что реализовано

- проверка Google ID token;
- Authorization Code Flow с PKCE S256 для Telegram и Yandex ID;
- одноразовый OAuth state с настраиваемым сроком действия;
- создание пользователей и внешних идентичностей без автоматического
  объединения разных провайдеров;
- собственные отзывные сессии War Chest;
- безопасная загрузка, нормализация и хранение аватаров в PostgreSQL;
- строгая конфигурация из YAML и переменных процесса;
- единый `AuthError` с кодами ошибок для HTTP-адаптера.

## Публичный API

Главная точка входа — `createAuth({ database, config?, configOptions? })`. Если
`config` не передан, пакет загружает его самостоятельно. Созданный объект
предоставляет:

- `loginWithGoogle(idToken)`;
- `beginTelegramLogin()` и `completeTelegramLogin(...)`;
- `beginYandexLogin()` и `completeYandexLogin(...)`;
- `getSession(sessionToken)` и `logout(sessionToken)`;
- `getAvatar(userId)`;
- имена session cookie и адрес успешного redirect из конфигурации.

Методы входа возвращают сессию и описание cookie, но не изменяют HTTP-ответ.
Методы начала redirect flow возвращают URL провайдера и отдельную cookie с
OAuth state. `getAvatar` возвращает бинарные данные, тип содержимого и hash либо
`null`; маршрут выдачи изображения реализует сервер.

Пакет также экспортирует `loadAuthConfig`, `AuthError` и публичные TypeScript-типы.
